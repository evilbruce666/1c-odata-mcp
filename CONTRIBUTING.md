# Как внести вклад

Спасибо за интерес к проекту! Issue и pull request приветствуются.

## Что попадает в основной репозиторий

Зачем развивается проект, что входит в его цели и как мы оцениваем предложения — в
[docs/DIRECTION.md](docs/DIRECTION.md). Ниже — правила разделения ядра и форков.

Этот репозиторий — **универсальный базовый коннектор** для Бухгалтерии 3.0 и типовых конфигураций.
На его основе делают форки под страны (Беларусь, Казахстан…), отраслевые и доработанные
конфигурации, условия конкретного провайдера. Чтобы основа оставалась небольшой и поддерживаемой,
каждый PR оценивается не только по качеству кода, но и по тому, нужен ли он всем.

**Берём:**

- исправления ошибок и совместимости с типовыми конфигурациями;
- функции, которые нужны большинству пользователей БП 3.0 — аналитика, документы, справочники;
- понятные сообщения об ошибках, безопасность записи, тесты и документацию;
- небольшие **точки расширения** (настройка, имя объекта в маппинге, параметр), если без них форк
  вынужден переписывать ядро.

**Оставляем в форке:**

- особенности национальных конфигураций, отраслевых и доработанных баз;
- обходы ограничений конкретного провайдера или хостинга;
- подсистемы, которые нужно вручную синхронизировать с кодом (большие реестры, дублирующие описания);
- фоновую работу, хранение состояния на диске пользователя, новые обязательные настройки — если без
  них обходится большинство.

**Замкнутый путь — всегда в ядре.** Если инструмент ядра сам создаёт состояние документа или
позволяет довести его до опасного действия (проведения, записи), то обнаружить это состояние и
исправить его тоже должно быть можно инструментами ядра. Редкость сценария тогда не повод
отправлять исправление в форк. Подсказки и предупреждения ведут только к инструменту, который
действительно это умеет: его входная схема принимает нужные данные.

**До большого PR откройте issue** с задачей и предполагаемым объёмом — обсудим, ядро это или форк,
и какой минимальной точки расширения хватит. Большие изменения лучше присылать несколькими PR, каждый
со своей пользой. Отказ взять функцию в ядро — не оценка её качества: в форке она может быть
к месту.

## Разработка

Нужен **Node.js ≥ 20**.

```bash
git clone https://github.com/evilbruce666/1c-odata-mcp.git
cd 1c-odata-mcp
npm install
npm run build        # сборка TypeScript → dist
npm test             # юнит-тесты (без живой базы)
npm run lint         # ESLint
npm run format       # Prettier (форматирование)
npm run typecheck    # проверка типов
npm run manifest     # пересобрать инструменты в manifest.json из живого сервера
```

Перед PR одной командой прогоните то же, что и CI (линтер, форматирование, типы, сборка, тесты):

```bash
npm run check
```

Если упало форматирование — `npm run format`. Своей базы 1С для этого не нужно: тесты идут против
снимка схемы БП 3.0 и «поддельной 1С» (см. ниже).

## Тесты

- **Юнит-тесты** (`test/`, Vitest) проверяют чистую логику без обращения к 1С —
  билдер запросов, разбор конфигурации, классификацию метаданных, ошибки. Их
  достаточно для большинства правок.
- **Проверка на живой базе** делается вручную read-only probe-скриптами
  (`dist/scripts/probe-*.js`, запуск `node --env-file=.env …`) — секретов они не
  печатают. Для пишущих изменений тестируйте на **тестовой/копии** базы.

### Снимок схемы БП 3.0

Заглушки 1С в тестах легко написать «как кажется», а не как в настоящей конфигурации: тест
проходит, а на базе 1С отвечает, что поля нет. Поэтому в репозитории лежит снимок `$metadata`
типовой Бухгалтерии 3.0 — `test/fixtures/metadata/bp30.xml`: объекты, которые использует
коннектор, их табличные части, функции регистров (`Balance`, `Turnovers`, `SliceLast`… с
параметрами), связи ссылочных полей (`Association` — на какой объект ведёт `Контрагент_Key`) и все
перечисления (только схема, данных базы в нём нет). Обновляется `npm run snapshot:metadata`.

- `test/metadata-snapshot.test.ts` прогоняет инструменты создания в режиме предпросмотра по этой
  схеме: каждое поле шапки и строк должно быть у объекта, а вид операции — среди значений
  перечислений. Новый инструмент записи — добавьте его в `CASES` этого теста.
- В своих тестах берите схему из снимка, а не пишите вручную: `bp30Metadata()`, `bp30Fields()` и
  `bp30Enums()` из `test/helpers/metadata-snapshot.ts`.
- Типичные расхождения, которые ловит снимок: в банковских документах контрагент составной
  (`Контрагент` + `Контрагент_Type`, поля `Контрагент_Key` нет); вид операции поступления от
  покупателя — «ОплатаПокупателя».
- Обновить снимок (например, после нового объекта в `src`):
  `npm run snapshot:metadata -- --db <имя базы>` — скрипт снимет `$metadata` и оставит только
  объекты, упомянутые в исходниках. Перед коммитом просмотрите дифф.

### Поддельная 1С и бюджет запросов

`test/fake-1c.test.ts` прогоняет **все** инструменты (чтение как есть, запись в предпросмотре) против
«поддельной 1С» — `test/helpers/fake-1c.ts`. Она подменяет `fetch` и отвечает как OData типовой
БП 3.0 по снимку схемы: неизвестный объект — 404, поле, которого нет у объекта (в `$select`,
`$filter`, `$orderby`, в теле записи или в строке табличной части), — 400, функция регистра или её
параметр, не объявленные в `$metadata`, — 400, вид операции не из перечислений — ошибка 1С. Данные
синтетические, по одной строке на объект.

Каждый инструмент проходит три прогона:

- только с обязательными аргументами — должен ответить без ошибки;
- со **всеми необязательными** аргументами (фильтры, суммы, периоды) — без обращений к
  несуществующим полям;
- инструменты «для любого документа» (`search_documents`, `get_document`, проводки, история) — по
  **каждому виду документа** из маппинга.

Ответ любого инструмента — не больше **50 000 символов** (`MAX_RESPONSE_CHARS`): больший ответ клиент
обрежет или не поместит в контекст модели. Большой отчёт делайте сводкой, подробности — по фильтру.

- Новый инструмент попадает в тест автоматически: аргументы подбираются по его схеме. Если по
  имени поля подобрать не удалось — добавьте их в `OVERRIDES`, взаимоисключающие необязательные
  аргументы — в `OPTIONAL_OMIT`.
- Известная, но ещё не исправленная ошибка схемы записывается в `KNOWN_VIOLATIONS`: тест проверяет,
  что она по-прежнему воспроизводится, и попросит убрать строку, когда её исправят.
- Для своих тестов: `fake1C()` возвращает `ctx` / `conn`, список запросов и нарушений.
- Посмотреть запросы инструмента: `FAKE_1C_TRACE=1 npx vitest run test/fake-1c.test.ts -t <имя>`.

**Бюджет запросов.** На облачной 1С каждый запрос — около секунды, поэтому число обращений к 1С на
каждый инструмент зафиксировано в `test/fixtures/request-budget.json`. Стало больше — тест падает
с текстом «X делает N запросов вместо M». Если рост осознанный (новая проверка, новые данные),
обновите норму командой `npm run budget:update` и объясните рост в описании PR.

### Сверка записи после потерянного ответа

`test/write-reconciliation.test.ts` прогоняет каждый инструмент с `operationId`: предпросмотр →
подтверждение, на котором ответ 1С «теряется», → журнал и `write.operation.status`. В журнале
должен остаться способ сверки — назначенный `Ref_Key` (`prepareCreate` по умолчанию) или проверка
`check` (как число строк у правки документа). Без них статус после таймаута не отличит «не дошло»
от «создано» и посоветует повторить — так получаются дубли. Новый инструмент записи добавьте в
`ARGS` этого теста; тест упадёт, если инструмент с `operationId` в нём не описан.

### Живой прогон чтения

Поддельная 1С проверяет, что запросы корректны по схеме, но не то, что в ответе есть нужные данные.
Перед релизом прогоните чтение на настоящих базах — ничего не пишет, любая попытка записи
блокируется и считается провалом:

```bash
npm run test:live:read                  # все базы из .env, ~1–2 мин
npm run test:live:read -- --db <имя базы>
```

Проверяет `health_check`, все инструменты чтения без обязательных аргументов и что у проводок
последних проведённых банковских документов и реализаций действительно приходят субконто. Так
нашлось, что записи регистра БП 3.0 субконто не публикуют вовсе. Код возврата 1 — что-то не прошло.

### Живой прогон записи

Юнит-тесты не ловят то, что зависит от конфигурации 1С (так нашлись ложный отказ подтверждения
договора и поиск по метке, ломавший запрос). Перед релизом с изменениями записи прогоните все
инструменты создания и правки строк на настоящей (лучше тестовой) базе:

```bash
npm run test:live -- --db <имя базы> --yes          # ~1 мин
npm run test:live -- --db <имя базы> --yes --slow   # + сценарий «правка не дошла», ещё 2 мин
```

Прогон создаёт объекты с меткой `ZZ-TEST live …`, проверяет предпросмотр → подтверждение →
повтор, потерянный ответ и сверку `write.operation.status`, а в конце помечает всё созданное на
удаление (удалить физически — «Удаление помеченных объектов» в 1С). Нужны `READ_ONLY=false` и
`WRITABLE` для базы; журнал операций — во временном каталоге. Код возврата 1 — что-то не прошло.

Нет своей базы 1С для проверки — поставьте на PR метку `needs-live-test`: мейнтейнер прогонит
изменение на тестовой базе и напишет результат в PR.

## Подводные камни 1С

Что OData типовой БП 3.0 делает не так, как подсказывает форма документа. Всё это уже встречалось
в живых базах; новое — дописывайте сюда.

**Поля и значения**
- Контрагент в банковских и кассовых документах составной: `Контрагент` + `Контрагент_Type`, поля
  `Контрагент_Key` у них нет. Так же владелец банковского счёта — `Owner` + `Owner_Type`
  (фильтр по `Owner_Key` даёт 400).
- Виды операций — точные значения перечислений, без догадок: поступление от покупателя —
  «ОплатаПокупателя» (не «ОплатаОтПокупателя»). Проверяйте по снимку схемы (`bp30Enums()`).
- Реализация услуг сохраняет табличную часть «Услуги» только с `ВидОперации = "Услуги"`.
- У документов номер — `Number`, у справочников — `Code`; `$select` чужого поля даёт 400.

**Запись**
- Через OData не срабатывает автозаполнение формы: счета учёта номенклатуры, счета расчётов и
  авансов по договору 1С сама не подставит — их заполняет MCP (`withSettlementAccounts`). Меняя
  договор, меняйте и счёт расчётов, и счёт авансов.
- `Ref_Key` нового объекта MCP назначает при предпросмотре (`prepareCreate`, UUIDv1): повтор с ним
  1С отвергнет, а сверка после таймаута — простой GET. По UUIDv1 читается время создания.
- Тело пишущего запроса не повторяется автоматически; повтор — только подтверждением с тем же
  `operationId`.
- Нет прав у пользователя OData — 1С отвечает 500 «Нарушение прав доступа!», а не 401/403. Это
  однозначный отказ (`kind: auth`), а не сбой сервера: права проверяются до записи.

**Чтение и запросы**
- Записи регистра бухгалтерии (`AccountingRegister_Хозрасчетный_RecordType`) полей субконто не
  публикуют вовсе — их отдаёт виртуальная таблица `RecordsWithExtDimensions` (и карточка счёта, и
  проводки документа). Отбор `Recorder eq cast(guid'…', 'Document_…')` работает в обеих. У счёта
  без субконто по плану счетов 1С отдаёт `null` и в значении, и в `ExtDimensionType…_Key`.
- `Balance(Period=…)` — сальдо на начало момента. Закрытие месяца проводится в 23:59:59, поэтому
  остаток «на конец дня» берите на начало следующего дня (00:00:00).
- `RecordsWithExtDimensions` не принимает параметр `Account`; длинный `or` по счетам падает с
  «Превышение допустимой вложенности» — счета пачками по 10. Отбор по контрагенту —
  `cast(guid'…','Catalog_Контрагенты')`, без `cast` будет 500.
- `$filter` вместе с `$expand` на регистре бухгалтерии — 501; проводки документа читаются по
  составному ключу `(Recorder=…,Recorder_Type=…)?$expand=RecordSet`.
- `substringof` 1С превращает в регулярное выражение: скобки в строке поиска дают 500.
- Облачные 1С (Scloud и др.) выполняют запросы одной учётной записи по очереди, около секунды на
  запрос. Считайте запросы: справочные данные — через кэш (`cached`), не обходите иерархии и
  регистры на каждом создании документа без нужды.

## Стиль и коммиты

- Код форматируется Prettier и проверяется ESLint (в CI).
- Комментарии и сообщения для пользователя — на русском (целевая аудитория).
- Коммиты — в стиле Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `ci:` …).
