# История изменений

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/),
версии — по [семантическому версионированию](https://semver.org/lang/ru/).

## [Не выпущено]

### Добавлено

- `read.document.search_documents` ищет по номеру (`number`): «33» и «№ 0033» находят `0000-000033`, «1» — `00000000001` (префикс и ведущие нули не нужны), а также входящий номер документа контрагента — накладной поставщика, платёжки покупателя («ГК-22537», «0000-05893», с пробелами в конце) — только целиком. Нумерация в 1С каждый год своя — возвращаются все совпадения, свои номера выше входящих. Отбор на сервере, точное сравнение — в коннекторе.
- Вид документа простыми словами вместо технического имени: `kind` — `sales`, `customer_invoices`, `purchases`, `supplier_invoices`, `bank`, `cash`, `vat_invoices`, `warehouse`. Без `kind` и `entitySet` — поиск по всем основным видам сразу («все документы за 10 сентября», «документ №33»): виды опрашиваются по одному (облачная 1С одновременные запросы тормозит), в ответе — сколько найдено по каждому виду, какие пропущены из-за неприменимого фильтра и какие не прочитались. Поиск читает только поля сводки, без табличных частей.

- Читаемый предпросмотр записи: рядом с `payload`/`fields` — `view` для того, кто подтверждает. Подписи вместо технических имён («Договор контрагента», «Дата»), названия вместо GUID («Контрагент: ООО Ромашка», «Счет учета расчетов с контрагентом: 62.01 Расчеты с покупателями и заказчиками»), строки табличных частей, а у изменения — «было → станет» по текущим значениям объекта (очистка поля видна как «—»). При создании пустые и нулевые значения, «нет» и устаревшие реквизиты «Удалить…» не показываются. Названия — по связям `$metadata`; ради скорости не больше 4 справочников на предпросмотр, по важности (контрагент, договор, номенклатура, счета учёта; организации — из кеша), прочие ссылки остаются GUID; сбой чтения названий предпросмотр не ломает. Подтверждение отправляет прежний `payload` — меняется только ответ предпросмотра. Идея — из форка [1c-odata-mcp-kz](https://github.com/malikyantizhanov/1c-odata-mcp-kz) (#34).

- `write.document.align_bank_payment_amounts` — выравнивает единственную строку «Расшифровки платежа» существующего непроведённого банковского документа по сумме документа: сумма платежа и взаиморасчётов = сумма документа, курс и кратность 1, НДС по ставке строки. Только рубли и договор в рублях без условных единиц; несколько строк, валюта, неизвестная ставка — отказ, суммы не угадываются. Версия документа, предпросмотр «было → станет», журнал и контрольное чтение — как у `apply_bank_settlement_settings`. Закрывает путь «проверить → исправить → провести» без формы 1С (#61).
- `write.document.post_document` не проводит банковский документ, если сумма документа не равна сумме «Расшифровки платежа» или в строке с договором пуста сумма взаиморасчётов — отказ с причиной уже в предпросмотре: 1С такой документ проведёт, но проводки по расчётам будут неверными или не сформируются. `apply_bank_settlement_settings` о том же предупреждает (`warnings`) (#61).

### Изменено

- Схема из `$metadata` знает цель ссылочных полей: связь (`Association`) даёт объект, на который ведёт `Контрагент_Key`, и кратность. Раньше вместо цели была роль связи. Снимок схемы в тестах включает связи.
- Переход на MCP SDK 2.x: `@modelcontextprotocol/server` 2.3.1 вместо `@modelcontextprotocol/sdk` 1.x (ветка 1.x получает исправления как минимум до конца января 2027 и остаётся на спецификации 2025-11-25; новые ревизии протокола — только в 2.x). Пакет стал легче: 26 рабочих зависимостей вместо 116 — ушли `express`, `hono`, `cors`, `ajv` и другие, ненужные серверу на stdio; `npx -y 1c-odata-mcp` ставится быстрее. Набор инструментов и их поведение не менялись; схемы инструментов — объекты `z.object(...)` (Standard Schema).

### Исправлено

- Подсказка после создания банковского документа с пустой суммой взаиморасчётов советовала `write.entity.update_entity`, который табличную часть не меняет. Теперь — инструменты, которые это исправляют: счёт расчётов — `apply_bank_settlement_settings`, сумма — `align_bank_payment_amounts` (#61).
- Изменение объекта (`write.entity.update_entity`, `update_counterparty`, `update_nomenclature`, `move_to_folder`, `update_document_lines`) больше не отвечает `updated: true` по одному ответу на PATCH: изменённые поля шапки перечитываются и сравниваются с отправленными с учётом типов (GUID в любом регистре, дата без времени, пустая ссылка). Успех — `verified: true`; если 1С приняла запрос, но сохранила не всё (например, банковский документ при записи перезаполнил договор из «Расшифровки платежа»), — ошибка с именами несохранённых полей, без повтора. Табличные части этим путём не сверяются — тогда `verified: false` и пометка `readbackNote`. Для банковских документов — подсказка менять договор и счета через `apply_bank_settlement_settings` (#60).

- `write.document.post_document` без `expectedDataVersion` больше не сообщает об успехе по одному коду 200: признак `Posted` и версия документа читаются до и после действия, успех — только если документ действительно проведён (при повторном проведении — сменилась версия) или проведение снято. Иначе — ошибка с ответом 1С; если документ не удалось перечитать — просьба сверить в 1С до повтора. Идея — из форка [1c-odata-mcp-kz](https://github.com/malikyantizhanov/1c-odata-mcp-kz) (#34).
- HTML-страница вместо ответа OData (публикация 1С и 1cfresh так отвечают на отказ доступа или исключение сервера, с кодом 200) — понятная ошибка с заголовком страницы вместо «Unexpected token '<'», без бесполезных повторов; для записи — предупреждение, что исход неизвестен. Битый JSON тоже больше не считается сетевой ошибкой (#34).

## [0.11.0] — 2026-10-23

Надёжность записи: статус операции больше не разрешает повторную запись по таймауту без решения человека, текст ошибки 1С сохраняется в журнале. Проводки документа показывают субконто на реальной БП 3.0. Явное повторное проведение и точная диагностика доступа OData — от [@alexpostnik](https://github.com/alexpostnik) (PR #51, #47).

### Добавлено

- Необязательный предел одновременных HTTP-запросов к одной базе: `ODATA_MAX_CONCURRENT_REQUESTS` (по умолчанию 0 — без предела, поведение прежнее) и `ODATA_QUEUE_TIMEOUT_MS`. Место держится на время запроса и чтения ответа, освобождается при ошибке и тайм-ауте и не держится во время паузы между повторами. Запрос, не дождавшийся места, в 1С не отправляется — запись в журнале закрывается как отклонённая, без «неизвестного исхода» (#57).

### Для контрибуторов

- `npm run test:live:read` — живая проверка на чтение против настоящих баз перед релизом: `health_check`, все инструменты чтения без обязательных аргументов и что у проводок реально приходят субконто. Любая попытка записи блокируется и считается провалом.
- Тест на снимке схемы БП 3.0 следит, чтобы проводки документа брали субконто из «Движений с субконто»: в тесте проводок записи регистра рисовались с субконто, которых у настоящей 1С нет, — поэтому баг #49 тесты не видели.
- `npm run test:live -- --slow` проверяет новое поведение `write.operation.status`: без `markNotApplied` операция не закрывается и через 2 минуты.
- В CONTRIBUTING — раздел «Что попадает в основной репозиторий»: проект остаётся универсальным базовым коннектором, особенности стран, конфигураций и провайдеров — в форках.
- «Поддельная 1С» проверяет функции регистров и их параметры по снимку схемы (в снимок добавлены объявления `Balance`, `Turnovers`, `SliceLast`…), прогоняет инструменты со всеми необязательными аргументами и инструменты «для любого документа» — по каждому виду документа; ответ инструмента — не больше 50 000 символов.
- Тест документации следит, чтобы README заканчивался разделом «Лицензия».

### Исправлено

- Точная диагностика доступа OData — от [@alexpostnik](https://github.com/alexpostnik) (PR #47). Если объекта нет в доступной схеме, сообщение больше не утверждает, что он «не опубликован», а называет возможные причины по порядку: «Состав OData», другое имя или отсутствие объекта в конфигурации, права. Отказ в правах (401/403 и 500 «Нарушение прав доступа!») называет HTTP-операцию, объект и действие `Post`/`Unpost` — без URL, параметров, ключей и данных ответа. `read.system.health_check` каждый раз перечитывает `$metadata` и обновляет кеш схемы для остальных инструментов — после изменения «Состава» перезапуск MCP не нужен. В `docs/CONNECTING.md` — порядок диагностики и что приложить администратору.
- `read.accounting.get_document_postings` показывает субконто проводок на реальной БП 3.0. Записи регистра (`_RecordType`) субконто не публикуют вовсе, поэтому раньше у проводок их не было никогда (проверено на двух живых базах). Теперь субконто берутся из «Движений с субконто» (`RecordsWithExtDimensions`, как в карточке счёта) по тому же регистратору и сопоставляются по номеру строки. У каждой стороны проводки — `dimensionsStatus`: `present`, `empty` (пусто или у счёта нет такого субконто), `not_in_schema` или `not_returned`; для двух последних в ответе пояснение `dimensionsNote` с причиной — это не «субконто пусты» (#49).
- `read.document.search_documents` с `minAmount` для документов без поля `СуммаДокумента` (перемещение, инвентаризация товаров и др.) больше не падает с ошибкой 1С 400: поле проверяется по схеме, и инструмент объясняет, что фильтр по сумме к этому типу неприменим (#45).
- Ошибки самого запроса, которые 1С отдаёт как HTTP 500 («Операция не разрешена в предложении ГДЕ», «Нельзя сравнивать поля неограниченной длины…»), больше не повторяются: раньше чтение отправлялось до 4 раз с паузами, хотя ответ не мог измениться. Текст 1С показывается в ошибке (#53).
- Журнал записи больше не теряет текст ошибки 1С при неизвестном исходе (например, HTTP 500). Сообщение «результат неизвестен» теперь включает ответ 1С, журнал хранит его (до 500 символов), а `write.operation.status` показывает его в поле `lastError` (#55).
- Подбор банковского счёта организации по названию (`orgBankAccount` в создании документов) больше не отвечает ложным «счёт не найден». Раньше читались только первые 200 счетов всех организаций, признак неполной выборки терялся, а ошибка чтения превращалась в пустой список. Теперь читается до 1000 счетов; если список всё равно неполный — по названию счёт не подбирается (нужен точный номер или `Ref_Key`), ошибка чтения показывается как есть, а без названия не подставляется случайный «первый» счёт из неполного списка (#54).
- `write.operation.status` больше не закрывает операцию как неприменённую (`not_applied`) только потому, что через 2 минуты созданного объекта или правки строк в 1С не видно. Клиент обрывает ожидание по таймауту, а 1С может закончить запись позже — совет «выполните новый предпросмотр» вёл к дублю. Теперь ответ `not_found` с просьбой сверить базу вручную; закрыть операцию можно только явно, `markNotApplied=true`, и не раньше чем через 2 минуты после попытки. Найденный при этом результат фиксируется как успех, а не закрывается (#52).
- Явное повторное проведение — от [@alexpostnik](https://github.com/alexpostnik) (PR #51, закрывает #46). `write.document.post_document` поддерживает повторное проведение `Posted=true` через `repost=true` вместе с `post=true` и `expectedDataVersion`. Сохраняются предпросмотр, подтверждение, журнал операции и удержание неизвестного исхода; версионный Post использует `PostingModeOperational=false` без Unpost. Первый успешный ответ возвращает уже прочитанный полный документ и явно ограничивает проверку состоянием документа, без утверждения о правильности проводок. Повтор завершённой операции возвращает только квитанцию без нового Post/GET. Старый неподтверждённый предпросмотр Post требует нового предпросмотра; завершённые квитанции сохраняют прежний отпечаток аргументов, если новый параметр не передан.

## [0.10.0] — 2026-10-22

Настройки счетов расчётов с контрагентами и перенос счетов в уже созданные банковские документы — от [@alexpostnik](https://github.com/alexpostnik) (PR #43). Карточка «Долги по срокам» прямо в ответе (MCP Apps). Проверки для контрибуторов: снимок схемы БП 3.0 и тест сверки записи.

### Добавлено

- **Настройки счетов расчётов** — `read.accounting.get_settlement_settings` / `write.accounting.set_settlement_settings` (и прежние имена `get_contract_settlement_settings` / `set_contract_settlement_settings` только для договора): чтение, создание и изменение точной записи регистра «Счета учёта расчётов с контрагентами» для договора, контрагента или группы. Изменение — с `expectedDataVersion` и If-Match, если версия опубликована; без версии — только с явным `singleWriter=true`. Предпросмотр, журнал операции и контрольное чтение; неизвестный исход удерживает повтор до ручной сверки.
- **Перенос счетов в существующий банковский документ** — `write.document.apply_bank_settlement_settings`: для непроведённого поступления или списания подбирает счёт расчётов и счёт авансов по сохранённым настройкам (договор → контрагент → группы → организация → общая) и ставит выбранный договор. Нужны явная сторона расчётов и `expectedDataVersion`; пустой контрагент заполняется только явно указанным `counterpartyRef`, заполненный не заменяется; остальные поля шапки и единственной строки платежа сохраняются и проверяются контрольным чтением. Договоры в условных единицах отклоняются понятным сообщением.
- **Группы контрагентов** — `write.counterparty.create_group` (новая группа с проверкой родителя и глубины) и `write.counterparty.set_group` (перенос отдельного контрагента в группу с If-Match; перемещение самих групп запрещено). `find_counterparty` ищет и группы (`subjectKind`) и возвращает родителя и версию объекта.
- **Проведение с проверкой версии** — `write.document.post_document` с `expectedDataVersion`: свой предпросмотр, журнал и чтение состояния после проведения или отмены. Без параметра работает как раньше.
- **Валюта регламентированного учёта по базе** — `ODATA_DB_<ИМЯ>_REGULATED_CURRENCY_CODE` (иначе общая `ODATA_REGULATED_CURRENCY_CODE`, затем 643); создание договора сравнивает валюту с ней, а не с жёстким 643.
- **Карточка «Долги по срокам» прямо в ответе** (MCP Apps) у `read.analytics.get_debtors` и `read.analytics.get_creditors`: итог, просрочено и в срок, полоса по срокам оплаты (без сроков в договорах — по возрасту долга), должники с мини-полосами, авансами и пометкой «старше года». Показывается в клиентах с поддержкой MCP Apps (проверено в MCPJam Inspector); **в Claude Desktop и Claude Code пока не показывается** — приложение не рисует карточку у инструментов с точкой в имени, ошибка передана Anthropic ([anthropics/claude-code#104045](https://github.com/anthropics/claude-code/issues/104045)). Клиенты без MCP Apps получают прежний текстовый ответ. Самодостаточный HTML без внешних загрузок, строки из 1С выводятся только как текст.

### Исправлено

- **Отказ 1С в правах больше не «неизвестный исход».** Ответ 500 «Нарушение прав доступа!» (у пользователя OData нет прав на объект или действие) теперь — однозначный отказ с понятным текстом «Нет прав в 1С…»: операция записи помечается отклонённой, `write.operation.status` отвечает «1С отклонила запись», можно исправить права и сделать новый предпросмотр. Раньше такая запись блокировалась как «результат неизвестен, сверьте вручную».
- Пишущие запросы, включая проведение и отмену проведения без тела, больше не повторяются автоматически; повтор по таймауту — только для чтения.

### Проверки

- Живая проверка новых инструментов на БП 3.0.208.14 / платформе 8.5.1.1302 (облако): перенос счетов в списание (оплата поставщику) и поступление (оплата покупателя) — запись подтверждена контрольным чтением; потерянный ответ при создании группы сверяется без дубля; отказ в правах на регистр настроек возвращается понятным отказом. Существующие инструменты записи — `test:live` 38 из 38.
- Белорусская Бухгалтерия 2.1.62.5 / платформа 8.3.25.1546 (тестовая база автора PR, предыдущие версии изменений): создание настройки договора, подбор счёта из настройки группы, перенос в банковские документы и проведение с чтением проводок.
- Не проверено вживую: подбор из особой настройки договора или группы на БП 3.0 (у нашего пользователя OData нет прав на запись регистра настроек); полное совпадение с правилами приоритета самой 1С и одновременная запись несколькими пользователями.

### Прочее

## [0.6.0] — 2026-10-03

Учётная аналитика: ОСВ по счёту, проводки документа и хронология документа для аудита. Идея и первая
реализация всех трёх инструментов — **[@AlexMarinenko](https://github.com/AlexMarinenko)** ([#31]);
мы проверили их на живых базах и доработали (чистое сальдо, проводки после проведения). Плюс защита
от повтора для строк документа, назначенный `Ref_Key` и договор по умолчанию.

### Добавлено

- **`read.accounting.get_account_turnover` — ОСВ по счёту.** Сальдо на начало,
  обороты и сальдо на конец (Дт/Кт) по произвольному счёту или префиксу (`51`, `60`,
  `62`, `90.01`) за период, итогом и по субсчетам. Источник — виртуальная таблица
  `BalanceAndTurnovers` регистра бухгалтерии Хозрасчетный; счёт и организация
  фильтруются на стороне 1С. Суммы — в копейках; при превышении
  `ODATA_ANALYTICS_MAX_ROWS` — явная ошибка вместо неполной ведомости.
- **`read.accounting.get_document_postings` — проводки документа.** Все записи
  регистра бухгалтерии Хозрасчетный, сформированные одним документом-регистратором
  (любой `Document_*`): Дт/Кт (код, наименование, Ref_Key счёта, субконто),
  сумма, количество/валютная сумма, итоги Дт/Кт и свод по корреспонденциям.
  Пример: `{"documentEntity": "Document_РегламентнаяОперация", "documentRef": "919a75d1-…"}`.
  Только GET; отбор по регистратору — на стороне 1С; поля записей сверяются с
  `$metadata`; несуществующий документ, незнакомая структура записей и превышение
  `ODATA_ANALYTICS_MAX_ROWS` — явные ошибки. Счета резолвятся пакетно, суммы — в копейках.
- **`read.audit.get_document_history` — хронология документа (аудит).** Только то,
  что доказуемо по стандартному OData, раздельно: `documentDate` (Document.Date —
  учётная дата) и `refCreatedAt` — метка генерации `Ref_Key`, выведенная из UUIDv1
  (`confidence: "derived"`, UTC, ISO-8601; не проверенное время создания/выполнения/
  проведения). Для UUID другой версии/варианта метка не возвращается. `executedAt` и
  `modifiedAt` недоступны и не возвращаются. Плюс: ответственный (реквизит документа,
  имя из `Catalog_Пользователи`; сбой поиска имени — статус, а не ошибка), `DataVersion`
  как есть, наличие движений в Хозрасчетном (один GET с `$top=1` по регистратору;
  `unsupported`/`error` отличимы от «движений нет»), `evidence` и `limitations`.
  Исследование источников — [docs/AUDIT-HISTORY.md](docs/AUDIT-HISTORY.md).
- **ОСВ поясняет «красное» сальдо.** `get_account_turnover` отдаёт чистое сальдо `openingNet` /
  `closingNet` (Дт − Кт), а если в колонке Дт или Кт отрицательное значение (развёрнутое сальдо по
  аналитике), объясняет это в `note` — на счёте 62 базы ООО так и было.
- **`post_document` показывает проводки.** После проведения в ответе — число проводок, итоги Дт/Кт и
  свод по корреспонденциям (`get_document_postings`); сбой чтения проводок проведение не отменяет.
- **Защита от повтора для добавления и удаления строк документа.** `add_document_line` и
  `remove_document_line` перечитывают документ, поэтому слепой повтор после таймаута добавлял ещё
  одну строку или удалял соседнюю. Теперь они, как и создание, требуют `operationId` из
  предпросмотра и идут через журнал; `write.operation.status` сверяет их по числу строк документа
  (`found_reconciled` / `not_applied`). Повтор уже подтверждённой операции отвечается из журнала
  до повторного чтения 1С. Проверено на живой базе, включая потерянный ответ.

- **Назначенный `Ref_Key` при создании.** Проверено на живой базе: 1С принимает ссылку от клиента,
  а повтор с той же ссылкой отвергает («нарушено условие уникальности»). Теперь MCP назначает
  `Ref_Key` (UUIDv1, как у ссылок самой 1С — время создания из неё по-прежнему выводимо) при
  предпросмотре и отправляет его при подтверждении. Дубль невозможен на уровне базы, а
  `write.operation.status` сверяет создание простым GET по ссылке — теперь и для справочников
  без «Комментария» (раньше — вручную).

- **`npm run manifest`** пересобирает инструменты в `manifest.json` из живого сервера и
  синхронизирует версию; **тест согласованности** сверяет манифест, версию, раздел CHANGELOG и
  число инструментов в README / `package.json` с кодом — расхождения ловятся до релиза.

- **`health_check` показывает журнал операций** (когда запись включена): доступен ли каталог для
  записи и сколько операций ждут сверки (исход неизвестен), с их id — чтобы они не терялись.

### Изменено

- **Метка `[op:…]` в «Комментарии» выключена по умолчанию** (`ODATA_WRITE_OPERATION_MARKER=true`
  включает): сверка теперь по `Ref_Key`, а видимая бухгалтеру метка больше не нужна. Операции из
  0.5.0, созданные с меткой, `write.operation.status` по-прежнему находит по ней.

### Исправлено

- **Сверка операций 0.5.0 по метке падала для справочников** (контрагент, номенклатура, договор…):
  `write.operation.status` запрашивал поле `Number`, которое есть только у документов, и 1С отвечала
  400. Теперь у справочников берётся `Code`. Найдено живым прогоном: операция создана опубликованной
  0.5.0, ответ «потерян», сверка новой сборкой — `found_reconciled`.
- **Реализации, созданные без договора, не проводились** — 1С (БП 3.0) падала невнятной ошибкой
  модуля прослеживаемости «Преобразование значения к типу Булево» (`create_act`, `create_shipment`
  и другие документы с контрагентом). Причина — пустой договор. Теперь, как форма 1С при выборе
  контрагента, MCP подставляет договор, если у контрагента он ровно один нужного вида с этой
  организацией (покупательские документы — «с покупателем», закупочные — «с поставщиком»);
  несколько или ни одного — не угадывает, а предупреждает в предпросмотре. `post_document` до вызова
  1С понятно сообщает, что договор не заполнен, и подсказывает, как его указать. Проверено на живой базе.
- **Неверные виды операций в описаниях денежных документов:** ПКО — `ОплатаПокупателя` (не
  `ПоступлениеОплатыОтПокупателя`), списание с р/с — `ПеречислениеЗП`. Если 1С отвергает значение
  перечисления, к ошибке теперь приложен список допустимых значений из `$metadata`.

- Журнал операций создаётся при первой записи: `ODataClient` больше не требует `writeJournalDir`
  для чтения.

### Прочее

- Зависимости: MCP SDK 1.32, pino 10.4, eslint 10.12, @types/node 26.6.4; `npm audit` — 0 уязвимостей.
  TypeScript 7 пока не берём: typescript-eslint поддерживает только `<6.1`.
- Проверки: 226 тестов; живой прогон записи на базе ИП — 39 из 39 сценариев.

## [0.4.0] — 2026-08-21

Запись документов доведена до боевого применения. Основу внёс
**[@Alexsab](https://github.com/Alexsab)** (PR [#19], [#20], [#21]) — он нашёл и
починил то, что не ловится юнит-тестами, только живой базой 1С. Его работа влита
целиком; несколько правок того же класса мы доделали сверху — отмечены как «нашли
при ревью».

### Добавлено

- **`write.document.copy_document` — документ по образцу.** Читает документ целиком
  и пишет копию со ВСЕМИ реквизитами (содержание строк, счета учёта, банковский
  счёт, ответственный, адрес доставки). `create_*` собирают документ из полей своей
  схемы и всё остальное теряют, поэтому ежемесячный документ приходилось дописывать
  руками. Копия непроведённая, номер присваивает 1С; правки — `date`, `fields`
  (шапка), `lines` (строки по номеру). Закрывает и «создать на основании».
- **`content` — реквизит «Содержание»** в строках продажных и закупочных документов.
  Раньше его принимал только счёт поставщика, а в остальных документах поле
  оставалось пустым — 1С его не заполняет сама. Для услуг это блокировало
  выставление: именно «Содержание» печатается в счёте и УПД.
- **Явные счета доходов/расходов** — `incomeAccount` / `expenseAccount` на строку и
  на документ. Значение — код как в 1С (`90.01.2`) или `Ref_Key`; неизвестный код
  даёт понятную ошибку, а не молчаливую подстановку. Приоритет: строка → документ →
  регистр «Счета учёта номенклатуры» → прежние умолчания. Документ, которому нужны
  90.01.2 / 90.02.2, раньше через OData было не создать вовсе.
- **`orgBankAccount`** в счёте покупателю, реализации и акте — название, номер счёта
  или `Ref_Key`. Реквизиты для оплаты печатаются в документе, выбирать их молча нельзя.

### Изменено

- **BREAKING: банковский счёт организации везде зовётся `orgBankAccount`.** Раньше
  один и тот же реквизит назывался в трёх инструментах по-разному — `bankAccount`
  (оплата, списание с р/с) и `orgAccountRef` (платёжное поручение), — и модель,
  выставив счёт, не находила знакомый параметр на оплате. Теперь имя одно, и все
  шесть инструментов принимают название, номер счёта или `Ref_Key` через общий
  резолвер: платёжное поручение раньше понимало только `Ref_Key`. Ломается мало:
  `bankAccount` не работал ни разу с момента появления из-за сломанного фильтра по
  полиморфному `Owner`, так что реально меняется только `orgAccountRef` →
  `orgBankAccount`.

### Исправлено

- **Правка строк документа с табличной частью «Услуги».** `add_document_line`,
  `remove_document_line` и `update_document_lines` читали и патчили только «Товары».
  Акт из `create_act` живёт в «Услугах» — строки уходили в пустую «Товары», сумма
  задваивалась, а удаление строки отвечало «в документе всего 0 строк». Теперь ТЧ
  определяется по факту; поддержан и «Акт об оказании производственных услуг».
- **Банковский счёт организации не подставлялся никогда.** Справочник фильтровался
  по `Owner eq guid'…'`, но `Owner` — полиморфная ссылка, и 1С отвечает на такой
  фильтр 500-й; ошибка гасилась в `catch`. То есть параметр `bankAccount` в
  `create_payment` и `create_bank_writeoff` не работал с самого появления. Теперь
  выборка сужается по `Owner_Type`, владелец сверяется на клиенте, приоритет:
  явный `Ref_Key` → название/номер → основной счёт организации.
- **Правка строк стирала реквизиты прежних строк.** Строка читалась в четыре поля,
  поэтому содержание, счета учёта и номенклатурная группа терялись при каждом
  добавлении или удалении строки. Теперь непересчитываемые поля переносятся как есть.
- **Ошибки ввода отделены от сбоев сервера.** Ненайденный склад, договор или счёт —
  неверные аргументы вызова, но `guard` подписывал им «Внутренняя ошибка
  инструмента». Введён `InputError`: текст отдаётся как есть.
- **Счёт-фактура на акт услуг получал нулевой НДС** *(нашли при ревью)*. Чтение
  документа-основания брало строки только из «Товаров», поэтому
  `create_issued_invoice` и `create_received_invoice` на акте выставляли
  `СуммаНДСДокумента: 0` — ошибка прямо в налоговом документе. НДС собирается по
  обеим табличным частям.
- **Сумма документа со смешанными ТЧ** *(нашли при ревью)*. У реализации бывают
  заполнены и «Товары», и «Услуги»; правка строк и `copy_document` считали итог
  только по правимой части и занижали его на вторую.
- **Сумма НДС строки не теряется при правке** *(нашли при ревью)*. При пересборке ТЧ
  `СуммаНДС` отбрасывалась всегда, и строки документа с НДС уезжали в 1С с нулевым
  налогом. Теперь переносится, если количество, цена, ставка и сумма строки не
  менялись. Пересчёт намеренно не делаем: формула зависит от `СуммаВключаетНДС` и
  процента ставки — угадывать такое нельзя.

`annotationsFor()` в `src/mcp/server.ts`: вместо regex-подбора по префиксу имени
теперь просто `name.startsWith("read.")`/`"write."`.

### Добавлено
- **`outputSchema` у всех 55 инструментов** — MCP-клиенты теперь могут типизировать

  большинство write-инструментов сводится к 4 переиспользуемым формам
  (`createResultSchema`/`patchResultSchema`/`mark_for_deletion`/`post_document` —

  покупателя с договором заполняется «Расшифровка платежа» (сч. 60/62,
  СпособПогашения=Автоматически); для налогов/ЗП/взносов — шапка без расшифровки.
  Создаются НЕпроведёнными; dry-run/confirm.
- Товарные складские документы (фаза 1), создание + построчное редактирование:
  `create_return_from_customer` (возврат от покупателя), `create_return_to_supplier`
  (возврат поставщику), `create_transfer` (перемещение между складами),
  `create_surplus` (оприходование), `create_writeoff` (списание), `create_inventory`
  (инвентаризация, не проводится). Счета учёта берутся из регистра/плана счетов
  (как у поступления/реализации); возвраты переиспользуют логику продажи/закупки.
  `update_document_lines`/`add_document_line`/`remove_document_line` теперь знают
  эти типы. Создаются НЕпроведёнными; dry-run/confirm. Чтение — как и прежде через
  `search_documents`/`get_document`.
- `create_payout_order` — создаёт «Платёжное поручение» (исходящая выплата контрагенту), всегда
  НЕПРОВЕДЁННЫМ. Номер задаётся явно вызывающим (для зеркалирования уже отправленной банковской
  платёжки тем же номером) — не автонумеруется, в отличие от прочих `create_*`. Счёт организации
  и валюта (рубль, код 643) резолвятся автоматически, если не заданы явно. dry-run/confirm, как у
  остальных инструментов записи.

## [0.1.8] — 2026-06-17

  месяца/дня) + проверка `from ≤ to`; раньше кривая дата уходила в OData как есть.
- В ответах аналитики — блок `scan` (`documentsScanned` / `windows` / `elapsedMs`):
  видно, что выборка полная и сколько просканировано.
