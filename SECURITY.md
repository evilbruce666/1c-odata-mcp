# Политика безопасности

## Поддерживаемые версии

| Версия | Исправления безопасности |
|---|---|
| 1.x (последняя минорная) | да |
| 0.x | нет — обновитесь до 1.x |

Что считается публичным API и как устаревают имена — [docs/VERSIONING.md](docs/VERSIONING.md).

## Сообщить об уязвимости

Пожалуйста, **не открывайте публичный issue** для уязвимостей.

Сообщайте приватно через GitHub:
<https://github.com/evilbruce666/1c-odata-mcp/security/advisories/new> (вкладка **Security → Report a vulnerability**,
приватные Security Advisories). Так детали не станут публичными до выпуска исправления.

Опишите проблему, шаги воспроизведения и потенциальное влияние.

**Как идёт раскрытие:**

1. Получение подтверждаем в течение 7 дней.
2. Воспроизводим, оцениваем влияние и сообщаем вам оценку и план.
3. Исправление выпускаем в поддерживаемой версии — как правило, не позже 90 дней с сообщения; срок согласуем с вами.
4. После выпуска публикуем advisory (с CVE, если уязвимость того требует) и, если вы согласны, называем вас в нём.

До публикации advisory детали не раскрываем ни мы, ни, просим, вы.

## Что стоит знать о безопасности проекта

- Сервер по умолчанию работает **только на чтение**; запись включается двумя
  независимыми предохранителями (`READ_ONLY=false` + `ODATA_WRITABLE=true` для одной базы или `ODATA_DB_<ИМЯ>_WRITABLE=true` для каждой из нескольких)
  и работает через предпросмотр/подтверждение.
- В базе без опубликованного регистра бухгалтерии «Хозрасчётный» (Управление торговлей и другие
  небухгалтерские конфигурации) запись запрещена, кроме проверенной для Управления торговлей: установки
  цен, справочников, складских и денежных документов, продаж и закупок — список в [docs/WRITE.md](docs/WRITE.md). Регистр с другим именем задаётся в
  [настройке учёта](docs/ACCOUNTING.md). Если проверить состав базы не удалось, запись тоже не выполняется.
- По умолчанию сервер — локальный процесс без сетевого порта. HTTP включается явно (`MCP_TRANSPORT=http`), только
  с токеном и по умолчанию только для чтения; запись по HTTP — при `READ_ONLY=false`, журнале на томе и инструментах
  записи поимённо в `TOOLS_ALLOW`, а кто подтверждает — ответственность интеграции; TLS в нём нет, вне внутренней сети нужен прокси. См.
  [docs/CONNECTING.md](docs/CONNECTING.md#подключение-по-http-опционально).
- Секреты (логин/пароль к OData) задаются через переменные окружения; пароль
  редактируется в логах и не попадает в репозиторий. Адрес OData с логином или паролем внутри сервер не принимает.
- Сервер обращается только к адресу вашей базы 1С: телеметрии и серверов проекта нет. Но ответы инструментов
  читает модель: у облачной модели они уходят её провайдеру — [docs/FAQ.md](docs/FAQ.md).
- Текст из 1С (наименования, комментарии, назначение платежа) читает модель, а написать его может любой, у кого
  есть доступ к базе. Ядро не пытается угадать «вредный» текст: чтение отдаёт данные как есть, инструкции сервера
  называют их данными, а не указаниями, читаемый предпросмотр показывает их одной строкой без символов, которые
  меняют вид на экране, а запись невозможна без предпросмотра этого же сервера. Подтверждает запись человек — следите,
  чтобы клиент показывал предпросмотр, а не подтверждал сам.
- Пользовательский ввод не подставляется в `$filter` напрямую — только через
  экранирующий билдер запросов.
- Рекомендуется отдельный пользователь 1С с минимально необходимыми правами и
  ограниченным «Составом OData».

## Сборка и выпуск

- Пакет публикуется в npm только из GitHub Actions по тегу, без токенов (Trusted Publishing), с provenance: в npm
  видно, из какого коммита и какого workflow он собран.
- Все сторонние действия в workflow закреплены хешем коммита, а не тегом, который можно передвинуть. Права токена у
  каждой задачи заданы явно и минимальны. Обновления действий и зависимостей предлагает Dependabot.
- К каждому релизу на GitHub приложен SBOM (`sbom.cdx.json`, CycloneDX) — состав зависимостей, которые ставятся
  вместе с пакетом.
- Код, который попадает в пакет, проверяется CodeQL при каждом изменении и раз в неделю; практики репозитория —
  OpenSSF Scorecard. Публикация в официальный реестр MCP идёт тем же тегом и только после того, как пакет появился
  в npm.
- Свойства на случайных входах (fast-check) проверяют экранирование значений в запросах к 1С, очистку текста на
  экране подтверждения и свод начислений налогов — [docs/TESTING.md](docs/TESTING.md#свойства-на-случайных-входах).
