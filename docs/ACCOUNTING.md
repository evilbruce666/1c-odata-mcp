# Настройка плана счетов и видов операций

Настройка относится к бухгалтерским конфигурациям. В Управлении торговлей плана счетов нет, и
настраивать там нечего: инструменты по счетам отвечают отказом, остатки, продажи и расчёты читаются
по регистрам оперативного учёта.

Без настройки сохраняются прежние значения БП РФ. Для другой конфигурации задайте
`ODATA_ACCOUNTING_CONFIG` (JSON) или `ODATA_DB_<ИМЯ>_ACCOUNTING_CONFIG` для конкретной
базы. Непустое значение базы заменяет весь глобальный JSON, без слияния полей.
Пустая строка или пробелы считаются отсутствием значения: база наследует глобальную
настройку, а пустая глобальная настройка включает прежние значения по умолчанию.
Ошибочный JSON и неизвестные поля останавливают запуск.

Синтетический пример для белорусской конфигурации — коды и виды операций должен
проверить бухгалтер по конкретной базе:

```json
{
  "chart": "ChartOfAccounts_Хозрасчетный",
  "register": "AccountingRegister_Хозрасчетный",
  "strictDefaults": true,
  "prefixes": {
    "receivables": ["62"],
    "payables": ["60"],
    "inventory": ["41"],
    "cash": ["50", "51", "52", "55", "57"]
  },
  "defaults": {
    "goods": ["41.1"],
    "incomingVat": ["18.3"],
    "outgoingVat": ["90.2"],
    "income": ["90.1"],
    "expense": ["90.4"],
    "receivable": ["62.1"],
    "receivableAdvance": ["62.2"],
    "payable": ["60.1"],
    "payableAdvance": ["60.2"]
  },
  "operationKinds": {
    "salesAct": "ПродажаКомиссия",
    "customerPayment": "ОплатаПокупателя"
  }
}
```

`ПродажаКомиссия` наблюдалось как принятое значение в одной белорусской TEST-базе.
Это не доказывает, что оно подходит для услуг во всех конфигурациях или соответствует
учётной политике вашей организации. Пример не является готовой учётной политикой.
Проверяйте допустимые элементы перечисления в `$metadata`, назначение операции и
результат на копии своей базы до использования.

`chart` задаёт опубликованный план счетов, `register` — регистр бухгалтерии для
аналитики. `prefixes` — префиксы счетов для дебиторки (`receivables`), кредиторки (`payables`),
остатков товаров (`inventory`) и денег (`cash`). Вид денег в `get_cash_balance` определяется
по первой части кода: 50 — касса, 51 — расчётные счета, 52 — валютные, 55 — спецсчета, 57 — в пути.

Проверка закрытия месяца (`read.accounting.check_month_close`) рассчитана на план счетов БП РФ:
после закрытия в нуле должны быть 90 и 91 (и обычно 25, 26), ОС и НМА — на 01 и 04. Эти коды не
настраиваются; для другого плана счетов результат этой части проверки нужно сверить с бухгалтером.
При `strictDefaults` без `prefixes.cash` / `payables` / `inventory` или без счетов расчётов в
`defaults` соответствующая часть проверки красного сальдо пропускается с перечнем недостающих настроек.
Каждый массив `defaults` — коды-кандидаты в порядке предпочтения: берётся первый
найденный в плане счетов.
`strictDefaults: true` запрещает российские запасные значения: нужна явная настройка
только тех групп, которые действительно используются, и найденный опубликованный
счёт. При `false` или без флага отсутствующие группы наследуют прежние значения РФ;
если счёт не найден, сохраняется прежнее поведение с незаполненным полем.

Приоритет доходов/расходов: строка → документ → регистр счетов номенклатуры →
настройка по умолчанию. Настройка проверяется после более приоритетных источников.
Для услуг не требуется счёт товаров; для строк `БезНДС` не требуется счёт НДС.
Счета расчётов и авансов с контрагентом сначала берутся из регистра «Счета учёта
расчётов с контрагентами» (настройка договора → контрагента → организации → общая, с
учётом вида расчётов договора), и только недостающие — из групп `receivable` /
`receivableAdvance` / `payable` / `payableAdvance`. В строгом режиме defaults
требуются лишь для счетов, которых не дал регистр. У оплат по банку и кассе счета
расчётов и сумма взаиморасчётов ставятся в строки расшифровки платежа, шапка не
заполняется — как в документах, созданных в 1С. Копия документа (`copy_document`)
сохраняет счета исходного документа.

Вид расчётов договора («в валюте регламентированного учёта» / «в иностранной валюте» /
«в у.е.») определяется по признаку у.е. и коду валюты договора. Код регламентированной
валюты задаётся явно: `ODATA_DB_<ИМЯ>_REGULATED_CURRENCY_CODE` →
`ODATA_REGULATED_CURRENCY_CODE` → `643`. Пустое значение базы наследует общее;
пустое общее включает прежнее `643`. В режиме одной базы используйте
`ODATA_REGULATED_CURRENCY_CODE`. Пробелы по краям убираются; допускается код
справочника длиной до 100 символов без управляющих символов, без требования ISO.

Например, для двух баз в одном процессе:

```dotenv
ODATA_DB_BY_REGULATED_CURRENCY_CODE=933
ODATA_DB_RU_REGULATED_CURRENCY_CODE=643
```

**Для белорусской базы нужен код `933`**. При ошибочном `643` договор BYN считается
валютным, а чтение сохранённой настройки с видом регламентированной валюты отклоняется.
Если запуском управляет внешняя служба, она должна передавать эти переменные дочернему
процессу. Наличие настройки в коннекторе не означает, что служба её передала.
`read.system.health_check` показывает действующий `regulatedCurrency.code` и источник
`database` / `global` / `default`. Это диагностика настройки, а не автоматическое
определение валюты по названию базы, конфигурации или платформе.

## Границы совместимости изменённых функций

Как пользоваться настройками счетов расчётов, группами контрагентов и переносом счетов в банковские документы — в [SETTLEMENTS.md](SETTLEMENTS.md). Ниже — границы совместимости по конфигурациям.

Схема каждой базы читается и кешируется отдельным `Connection`; настройки счетов выше
тоже могут быть отдельными. Это существующие механизмы настройки. OData 3.0 обозначает
версию протокола, а не номер платформы или конфигурации. Наличие объекта в metadata
не доказывает права записи. `health_check: ok` подтверждает доступ к metadata и не
сертифицирует все инструменты, проводки или учётную политику.

| Возможность | Требуемая схема / поведение | Доказательство и предел |
| --- | --- | --- |
| Контрагент банковского документа | `Контрагент_Key: Edm.Guid` либо `Контрагент` + проверенный `Контрагент_Type` | Наблюдённая схема Беларуси 2.1 и снимок БП 3.0; синтетический предпросмотр обоих вариантов. |
| Оплата покупателя / поставщика | `ОплатаПокупателя` / `ОплатаПоставщику`, подходящее направление документа; ссылки счетов расчётов и авансов | Значения из снимка БП 3.0; обе стороны покрыты тестами. |
| Настройка счетов договора/контрагента/группы | Независимый непериодический `InformationRegister_СчетаУчетаРасчетовСКонтрагентами`, четыре точных ключа и нужные ресурсы | Versioned update: DataVersion + If-Match. При фактическом отсутствии DataVersion: явный singleWriter, без серверной блокировки. Другие схемы отклоняются. |
| Регламентированная валюта | Явный код + опубликованный `Catalog_Валюты.Code` | В одном процессе проверены 933 и 643 на искусственных данных, включая чтение точной настройки. Нет автоматического выбора валюты. |
| Применение счетов к существующему банковскому документу | Непроведённый документ, свежая DataVersion, один платёж, известные ссылки и валюта | PATCH сохраняет опубликованные значения шапки и строк; исключение — DataVersion и три зависимых поля строки: курс, кратность, сумма взаиморасчётов. Новые значения проверяются контрольным чтением. |
| Договоры в у.е. в apply_bank_settlement_settings | `РасчетыВУсловныхЕдиницах=true` | Не поддержаны: ранний явный отказ, даже при одинаковых валютах. Классификация/чтение настроек и старые инструменты не изменены этим отказом. |
| Группы и результат потерянного ответа | create_group: точный GET по назначенному Ref_Key; регистр: точный составной ключ и fingerprint полей | Повторная запись для сверки не отправляется; set_group с неизвестным результатом удерживается для ручной проверки. |

По сообщению владельца белорусская TEST использует платформу **8.3.25.1546**,
«Бухгалтерия для Беларуси» **2.1.62.5**, расширения «Исправления 2.1.62.5 (433)»
и «Расширение БПС txt». Эти номера заявлены владельцем, через OData не определялись;
поля и ключи затронутых объектов действительно наблюдались. Снимок российской БП 3.0
получен мейнтейнером; точные версия платформы и релиз БП **неизвестны**.

На наблюдённой белорусской публикации из констант доступна только
`Constant_ИспользоватьСтатьиДвиженияДенежныхСредств`; константа регламентированной
валюты не опубликована. [Руководство платформы 8.3.25, приложение 12.1](https://its.1c.ru/db/v8325doc/content/102/hdoc)
описывает `Constant_<Имя>`, `Value`, `SurrogateKey`; оно не делает неопубликованную
константу доступной через API. Поэтому для текущего исправления используется явная
настройка, а не предположение о доступном источнике валюты.

Общий профиль «инструмент → объекты/поля/операции/права» для всех конфигураций остаётся
отдельной задачей [#375](https://github.com/alexpostnik/1c/issues/375). Этот PR не
реализует полный диагностический механизм и не заявляет совместимость всех 74
инструментов. Исправленный head ещё не проверен на живой 1С: нужна отдельная
разрешённая проверка на TEST и повторный прогон мейнтейнера на БП 3.0.

`operationKinds.salesAct` — значение `ВидОперации` для `write.sales.create_act`
(по умолчанию `Услуги`); `customerPayment` — для `write.money.create_payment`
(по умолчанию `ОплатаПокупателя`). Параметр `operationKind` этих инструментов важнее
настройки базы. Настройка меняет только значение перечисления: состав документа и
смысл инструмента (акт с услугами / оплата от покупателя) сохраняются. Не выбирайте
операцию с другим составом полей или назначением. Другие инструменты с
`operationKind` уже требуют его явно и передают без замены. Производственный акт
`create_services_act` не отправлял `ВидОперации` и сохраняет это поведение.

Новая настройка вступает в силу после перезапуска сервера (для Claude Desktop — после
перезапуска приложения).
