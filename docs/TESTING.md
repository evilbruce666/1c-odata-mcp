# Тесты

- **Юнит-тесты** (`test/`, Vitest) проверяют чистую логику без обращения к 1С —
  билдер запросов, разбор конфигурации, классификацию метаданных, ошибки. Их
  достаточно для большинства правок.
- **Проверка на живой базе** делается вручную read-only probe-скриптами
  (`dist/scripts/probe-*.js`, запуск `node --env-file=.env …`) — секретов они не
  печатают. Для пишущих изменений тестируйте на **тестовой/копии** базы.

## Снимки схемы БП 3.0 и УТ 11

Заглушки 1С в тестах легко написать «как кажется», а не как в настоящей конфигурации: тест
проходит, а на базе 1С отвечает, что поля нет. Поэтому в репозитории лежит снимок `$metadata`
типовой Бухгалтерии 3.0 — `test/fixtures/metadata/bp30.xml`: объекты, которые использует
коннектор, их табличные части, функции регистров (`Balance`, `Turnovers`, `SliceLast`… с
параметрами), связи ссылочных полей (`Association` — на какой объект ведёт `Контрагент_Key`) и все
перечисления (только схема, данных базы в нём нет). Обновляется `npm run snapshot:metadata`.

- `test/metadata-snapshot.test.ts` прогоняет инструменты создания в режиме предпросмотра по этой
  схеме: каждое поле шапки и строк должно быть у объекта, а вид операции — среди значений
  перечислений. Новый инструмент записи — добавьте его в `CASES` этого теста.
- В своих тестах берите схему из снимка, а не пишите вручную: `bp30Metadata()`, `bp30Fields()` и
  `bp30Enums()` из `test/helpers/metadata-snapshot.ts`.
- Типичные расхождения, которые ловит снимок: в банковских документах контрагент составной
  (`Контрагент` + `Контрагент_Type`, поля `Контрагент_Key` нет); вид операции поступления от
  покупателя — «ОплатаПокупателя».
- Обновить снимок (например, после нового объекта в `src`):
  `npm run snapshot:metadata -- --db <имя базы>` — скрипт снимет `$metadata` и оставит только
  объекты, упомянутые в исходниках. Перед коммитом просмотрите дифф.

Второй снимок — **Управление торговлей 11.5**, `test/fixtures/metadata/ut11.xml` (`ut11Metadata()`):
регистры склада, продаж, расчётов с партнёрами и денег, ключи аналитики, справочники и документы
продаж, закупок, банка и кассы. В УТ нет регистра «Хозрасчётный» — на этой схеме проверяются отказы
инструментов бухучёта, отказ инструментов записи Бухгалтерии без аналога в УТ и допуск записи цен, справочников,
склада, денег, продаж и закупок УТ.

- Снимок снят с рабочей базы, поэтому **поля доработок из него убраны вручную** (`Б_*`, `Операции0`,
  `…ДляЗП` и подобные): в репозитории только типовая схема, без имён и данных клиента. Обновляя
  снимок, повторите это и проверьте дифф — в нём не должно быть ни нетиповых полей, ни значений.
- Тесты, фикстуры и примеры — только с синтетическими названиями складов, товаров и контрагентов.

## Справочник сроков и налоговый календарь

- `test/tax-calendar.test.ts` проверяет сам [tax-calendar.json](../tax-calendar.json): пересчитывает перенос каждой
  даты по производственному календарю, полноту набора по годам и отсутствие сумм. **С 1 декабря он требует правила
  на следующий год** — добавьте их по текстам статей НК РФ и производственный календарь этого года.
- `test/tax-calendar-tool.test.ts` — календарь на поддельной 1С со своими синтетическими строками (суммы и даты
  выдуманы). Поддельная 1С не применяет `$filter`, поэтому отборы проверяются по самому запросу или в коде.

## Совместимость с новым релизом конфигурации

1С выпускает релизы Бухгалтерии и Управления торговлей каждый месяц, и объекты или реквизиты в них меняются.
Чтобы узнать об этом до пользователей, после обновления тестовой копии базы:

1. Снимите схему копии: `npm run snapshot:metadata -- --db <база> --out <файл>`. Снимок рабочей базы содержит её
   доработки — держите его вне репозитория.
2. Прогоните все инструменты против этой схемы: `npm run compat -- --bp30 <файл>` для Бухгалтерии, `--ut11 <файл>`
   для Управления торговлей (можно оба сразу). 1С и сеть не нужны: проверяется схема.

Отчёт состоит из двух частей:

- **что пропало** по сравнению со снимком в репозитории — объекты и поля, которыми пользуется коннектор. Часть
  инструментов при пропавшем поле не падает, а отвечает без него, поэтому этот список важен сам по себе;
- **какие проверки не прошли** — инструменты, которые на этой схеме обращаются к несуществующему или отказывают.

«Нет объекта» бывает по двум причинам: его убрали в релизе или он не добавлен в «Состав OData» этой базы. Второе
лечится публикацией, первое — правкой коннектора и обновлением снимка (`npm run snapshot:metadata`, затем
проверка диффа, как описано выше). Код возврата `npm run compat` — 1, если есть пропавшее или непрошедшее.

## Поддельная 1С и бюджет запросов

`test/fake-1c.test.ts` прогоняет **все** инструменты (чтение как есть, запись в предпросмотре) против
«поддельной 1С» — `test/helpers/fake-1c.ts`. Она подменяет `fetch` и отвечает как OData типовой
БП 3.0 по снимку схемы (или УТ 11 — `fake1C(env, { schema: "ut11" })`): неизвестный объект — 404, поле, которого нет у объекта (в `$select`,
`$filter`, `$orderby`, в теле записи или в строке табличной части), — 400, функция регистра или её
параметр, не объявленные в `$metadata`, — 400, вид операции не из перечислений — ошибка 1С. Данные
синтетические, по одной строке на объект.

Каждый инструмент проходит три прогона:

- только с обязательными аргументами — должен ответить без ошибки;
- со **всеми необязательными** аргументами (фильтры, суммы, периоды) — без обращений к
  несуществующим полям;
- инструменты «для любого документа» (`search_documents`, `get_document`, проводки, история) — по
  **каждому виду документа** из маппинга.

Ответ любого инструмента — не больше **50 000 символов** (`RESPONSE_CHARS_NORM`): больший ответ клиент
обрежет или не поместит в контекст модели. Большой отчёт делайте сводкой, подробности — по фильтру.
На больших данных норму держат страницы: `pageOf` с `offset` и `snapshot` в инструменте, а у инструментов с `limit` без
своих страниц обёртка `limitResponseSize` сама добавляет `offset` (`test/response-size.test.ts`).

- Новый инструмент попадает в тест автоматически: аргументы подбираются по его схеме. Если по
  имени поля подобрать не удалось — добавьте их в `OVERRIDES`, взаимоисключающие необязательные
  аргументы — в `OPTIONAL_OMIT`.
- Известная, но ещё не исправленная ошибка схемы записывается в `KNOWN_VIOLATIONS`: тест проверяет,
  что она по-прежнему воспроизводится, и попросит убрать строку, когда её исправят.
- Для своих тестов: `fake1C()` возвращает `ctx` / `conn`, список запросов и нарушений. Свои строки
  ответа — `data: (q) => …`; поддельная 1С проверяет и `Condition` функций регистра, и `$expand` по
  связям схемы.

**Инструмент для другой конфигурации.** Один факт — один инструмент: если тот же факт в другой
конфигурации хранится иначе (документ называется по-другому, поле договора составное), инструмент
читает схему базы и выбирает поле сам (`src/odata/doc-fields.ts`, кандидаты имён в
`src/config/mapping.ts`). Другой факт — другой инструмент: управленческие расчёты с партнёрами в УТ —
не счёт 62 бухучёта, поэтому это `get_partner_settlements`, а не режим `get_debtors`. Инструмент
бухучёта в базе без «Хозрасчётного» отвечает отказом с подсказкой (`requireEntity`, `refuseOnTrade`
в `src/odata/publication.ts`). Новому инструменту нужны тесты на обеих схемах.
- Посмотреть запросы инструмента: `FAKE_1C_TRACE=1 npx vitest run test/fake-1c.test.ts -t <имя>`.

**Бюджет запросов.** На облачной 1С каждый запрос — около секунды, поэтому число обращений к 1С на
каждый инструмент зафиксировано в `test/fixtures/request-budget.json`. Стало больше — тест падает
с текстом «X делает N запросов вместо M». Если рост осознанный (новая проверка, новые данные),
обновите норму командой `npm run budget:update` и объясните рост в описании PR.

## Сверка записи после потерянного ответа

`test/write-reconciliation.test.ts` прогоняет каждый инструмент с `operationId`: предпросмотр →
подтверждение, на котором ответ 1С «теряется», → журнал и `write.operation.status`. В журнале
должен остаться способ сверки — назначенный `Ref_Key` (`prepareCreate` по умолчанию) или проверка
`check` (как число строк у правки документа). Без них статус после таймаута не отличит «не дошло»
от «создано» и посоветует повторить — так получаются дубли. Новый инструмент записи добавьте в
`ARGS` этого теста; тест упадёт, если инструмент с `operationId` в нём не описан.

## Живой прогон чтения

Поддельная 1С проверяет, что запросы корректны по схеме, но не то, что в ответе есть нужные данные.
Перед релизом прогоните чтение на настоящих базах — ничего не пишет, любая попытка записи
блокируется и считается провалом:

```bash
npm run test:live:read                  # все базы из .env, ~1–2 мин
npm run test:live:read -- --db <имя базы>
npm run test:live:read -- --http        # те же проверки настоящим клиентом через HTTP-транспорт
```

Проверяет `health_check`, все инструменты чтения без обязательных аргументов (ответ должен проходить `outputSchema`, как у настоящего клиента) и что у проводок
последних проведённых банковских документов и реализаций действительно приходят субконто. Так
нашлось, что записи регистра БП 3.0 субконто не публикуют вовсе. Код возврата 1 — что-то не прошло.

Ещё он сверяет серверный отбор по полиморфному «Контрагент» банка и кассы (`cast`, `src/scripts/live-poly.ts`)
с прежним способом: читает все банковские и кассовые документы за 12 месяцев без отбора и отбирает у себя. Для
частых контрагентов, физлица или сотрудника, контрагента без документов и неизвестного guid документы
`search_documents` и итоги `get_payments_breakdown` должны совпасть с этим эталоном. В выводе видно, приняла ли
1С `cast` и сколько запросов ушло. На поддельной 1С сама проверка прогоняется в `test/poly-counterparty.test.ts`.

## Живой прогон записи

Юнит-тесты не ловят то, что зависит от конфигурации 1С (так нашлись ложный отказ подтверждения
договора и поиск по метке, ломавший запрос). Перед релизом с изменениями записи прогоните все
инструменты создания и правки строк на настоящей (лучше тестовой) базе:

```bash
npm run test:live -- --db <имя базы> --yes          # ~1 мин
npm run test:live -- --db <имя базы> --yes --slow   # + сценарий «правка не дошла», ещё 2 мин
```

На рабочей базе, где проводить нельзя, добавьте `--no-post`: сценарий «договор подставлен → акт проводится»
пропускается, остальное создаётся непроведённым. Документы получают комментарий с меткой ZZ-TEST, если
инструмент его принимает, — их можно найти поиском, даже если прогон оборвался. Итог живых проверок по каждому
инструменту — в [SUPPORT.md](SUPPORT.md).

Прогон создаёт объекты с меткой `ZZ-TEST live …`, проверяет предпросмотр → подтверждение →
повтор, потерянный ответ и сверку `write.operation.status`, а в конце помечает всё созданное на
удаление (удалить физически — «Удаление помеченных объектов» в 1С). Нужны `READ_ONLY=false` и
`WRITABLE` для базы; журнал операций — во временном каталоге. Код возврата 1 — что-то не прошло.

Управление торговлей — свой прогон на копии рабочей базы: тестовые справочники ZZ-TEST (находятся по наименованию
или создаются) и документы склада, денег, продаж и закупок организации из `--org` — создание, проведение со сверкой
движений, отмена, пометка удаления. Статьи, вид цен и вид номенклатуры берутся из последних проведённых документов
базы, поэтому в скрипте нет данных конкретной базы:

```bash
npm run test:live:ut -- --db <имя базы> --org <организация> --warehouse <склад> --yes   # [--warehouse2 <склад>] [--cash] [--bank]
```

Запись по HTTP (#67) — отдельный прогон: экземпляр коннектора в режиме `MCP_TRANSPORT=http` с записью только
установки цен проходит сценарий интеграции-бота — предпросмотр, рестарт процесса, подтверждение с обрывом соединения
клиентом, повтор подтверждения (ответ из журнала), `write.operation.status`, ровно один непроведённый документ в 1С.
Созданный документ скрипт называет — пометьте его на удаление:

```bash
npm run test:live:http -- --db <имя базы> --item <Ref_Key позиции> --yes   # [--price-kind <Ref_Key>] [--price 123.45]
```

Нет своей базы 1С для проверки — поставьте на PR метку `needs-live-test`: мейнтейнер прогонит
изменение на тестовой базе и напишет результат в PR.

## Сбои и повторы: подделка, которая помнит созданное

Обычная поддельная 1С отвечает синтетикой и не помнит, что в неё записали. Для сценариев «ответ потерян → повтор →
`write.operation.status` → новый предпросмотр» нужна база с состоянием: `test/trade-retry.test.ts` держит созданные
партнёров и контрагентов в памяти (находятся по ссылке и отбором по ИНН), подставляет сбой на каждый POST — ответ
потерян после записи, запрос не дошёл, отказ 1С — и перезапускает сервер на том же журнале. Критерий: ни второго
объекта, ни ложного успеха. Новый инструмент создания, у которого повтор может задвоить объект, — добавьте сюда.

## Свойства на случайных входах

`test/property.test.ts` (fast-check) прогоняет сотни случайных входов там, где ошибка дорога:

- строка, подстрока и GUID в запросе к 1С не выходят из литерала и читаются обратно без потерь, параметры
  запроса — ровно те, что заданы, при любом значении отбора, в том числе от модели в `read_register`;
- текст из 1С на экране подтверждения — одна строка без управляющих, невидимых и символов направления;
- свод начислений налогов: итог по счёту равен сумме активных строк, сторно переносит, но не теряет.

Генератор наполовину состоит из опасных символов: кавычки, `%`, `_`, `[`, обратная косая, переводы строк, U+202E и
соседние. На чисто случайном Юникоде они почти не выпадают, и снятое экранирование проходило незамеченным. Каждое
свойство проверено мутацией: снятое экранирование кавычки и символов ПОДОБНО, пропущенный символ направления,
сторно без переноса и неактивные строки в сумме — тест падает. При падении fast-check печатает минимальный пример и
`seed`, по нему пример воспроизводится.

## Проверка тестов мутациями

Зелёный тест ещё не значит, что он что-то проверяет. Каждый новый тест проверьте мутацией: сломайте защищаемую
строку кода (уберите проверку, подставьте константу, поменяйте поле) и убедитесь, что тест падает; затем верните
код. Тест, который проходит и на сломанном коде, — пустой: перепишите его. В описании PR назовите мутации и что
их ловит. Так нашлись, например, мёртвый код (исключение «своего» объекта при проверке дубля ИНН — мутация не
ловилась, потому что повтор отвечает из журнала раньше) и тест на дату, который не мог упасть, пока предпросмотр и
подтверждение шли в одну секунду (поймал `vi.useFakeTimers` с переходом через полночь).

- Запись в Управлении торговлей — строка в `TRADE_WRITE` (`src/mcp/server.ts`: какие вызовы и при какой схеме

- Норма запросов — `npm run budget:update`, рост объясните в PR.

- `npm run manifest` (manifest.json и справочник параметров), строка в [TOOLS.md](TOOLS.md), числа инструментов в

## Живая проверка на копии базы

Значения перечислений, поля, которые 1С заполняет сама, и отказы конкретной базы видны только на настоящей 1С
(так нашлись две «шт» в справочнике единиц и то, что УТ не даёт изменить номенклатуру через OData). Порядок:

1. Сначала только чтение: как заполнены объекты того же вида в базе (распределения перечислений, заполненность
   полей) — печатайте числа и значения перечислений, не названия.
2. Предпросмотр на живой базе — записи заблокированы в скрипте (`fetch` пропускает только GET).
3. Запись — с согласия владельца базы на конкретный предпросмотр; скрипт пропускает только ожидаемые запросы.
   Объекты — с меткой `ZZ-TEST`, после проверки контрольное чтение и пометка удаления.
4. Итог — в CHANGELOG: что проверено и на какой базе.
