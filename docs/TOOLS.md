# Инструменты

93 инструмента (45 чтение/аналитика + 48 записей). У всех есть необязательный параметр **`database`** (какая база 1С — см. `read.system.list_databases`); у аналитических — ещё и **`organization`** (фильтр по юрлицу — см. `read.system.list_organizations`).

**Чтение — в Бухгалтерии и в Управлении торговлей** (документы, справочники, схема; деньги — по счетам в Бухгалтерии и по регистрам денежных средств в УТ; в доработанных конфигурациях — если документы называются как в типовых):

| Инструмент | Что делает |
|---|---|
| `read.system.health_check` | Проверка соединения и авторизации |
| `read.system.data_freshness` | По какую дату внесены данные: последний документ по основным видам, сколько за 30 дней и сколько не проведено, будущие даты отдельно, последний закрытый месяц |
| `read.system.list_databases` / `read.system.list_organizations` | Список баз / организаций (для параметров `database` / `organization`) |
| `read.organization.get_organization_card` | Карточка организации: ИНН/КПП/ОГРН, ОКВЭД, налоговый орган, адреса, банковский счёт, директор и главный бухгалтер; режим налогообложения (`taxRegime`) |
| `read.schema.list_entities` / `read.schema.describe_entity` | Карта объектов базы и поля конкретного объекта (из `$metadata`) |
| `read.counterparty.find_counterparty` / `read.counterparty.get_counterparty` | Поиск контрагента (по названию/ИНН) с полным наименованием и ролями по договорам (покупатель, поставщик, комитент…) и его карточка; `subjectKind=group` — поиск групп контрагентов |
| `read.document.search_documents` / `read.document.get_document` | Поиск документов — по виду (`kind`: продажи, банк, касса…) или сразу по всем основным видам, по периоду и номеру (`number`: «33» находит 0000-000033, а также входящий номер контрагента) — и документ с табличной частью (`compact=true` — без пустых значений, с названиями рядом со ссылками); строки поиска называют контрагента и организацию; отбор по ответственному (`responsibleRef`) |
| `read.analytics.get_cash_balance` | Деньги сейчас или на дату: остатки 50/51/52/55/57 по каждому банковскому счёту и кассе, итоги «доступно», «спецсчета», «в пути». В Управлении торговлей — по регистрам денежных средств: расчётные счета, кассы, кассы ККМ, деньги в пути |
| `read.catalog.list_warehouses` | Склады справочника: Ref_Key, название, тип склада, путь папки, признаки папки и пометки удаления; отбор по части названия и типу. Отсюда берутся Ref_Key для отбора `warehouses` в остатках и продажах — в том числе склады без остатка |
| `read.catalog.list_items` | Номенклатура справочника — все позиции, в том числе без остатка и продаж: Ref_Key, название, артикул, код, папка и путь, пометка удаления, использование характеристик. Отбор по группе или списку групп с подгруппами и по части названия или артикулу; `ref` совпадает с `ref` в остатках и продажах, по нему список сопоставляется с ними |
| `read.catalog.list_users` | Пользователи 1С для выбора ответственного документа (`responsibleRef`): имя, признаки «недействителен» и «служебный», подразделение; поиск по частям имени; по умолчанию только действующие; `refs` — проверка привязок. Контактов и кадровых данных нет |
| `read.analytics.get_prices` | Действующие цены по видам цен на момент (Управление торговлей 11, Бухгалтерия 3.0 — по типам цен; КА 2 и ERP 2 — по тем же полям, что УТ, без проверки): срез последних по регистру цен, прежний механизм и ценообразование 2.5 (2.5 — без проверки на живой базе). Отбор по видам цен, группам номенклатуры, поиску и списку позиций; у каждой цены — с какого момента она действует |
| `read.analytics.get_sales` / `read.analytics.get_cashflow` | Продажи за период (сумма документов, при агентской схеме с деньгами комитентов; выручка в учёте — оборот 90.01) / движение денег (банк + касса) |
| `read.analytics.get_sales_breakdown` / `read.analytics.get_purchases_breakdown` | Продажи/закупки с разбивкой по контрагенту, месяцу, договору, категории (ИП/ЮрЛицо/…) |
| `read.analytics.get_payments_breakdown` | Приход/расход по виду операции, месяцу, контрагенту, статье ДДС — «сколько заплатили ИП за год», «проценты по депозиту» |
| `read.analytics.get_taxes_paid` | Уплаченные налоги и взносы за период, с разбивкой по виду налога |
| `read.analytics.get_deal_history` | Хронология движений по сделке (код в назначении платежа) или договору |
| `read.counterparty.get_customer_history` / `read.counterparty.get_supplier_history` | История взаиморасчётов с покупателем / поставщиком |
| `read.audit.get_document_history` | Хронология документа для аудита: учётная дата (`documentDate`) отдельно от метки генерации `Ref_Key` из UUIDv1 (`refCreatedAt`, derived), ответственный, `DataVersion` как есть, наличие движений в Хозрасчетном, evidence и limitations. Фактическое время выполнения/изменения через стандартный OData недоступно — не возвращается |
| `read.schema.read_register` | Строки любого опубликованного регистра, когда профильного инструмента нет: выбранные поля, отборы по типам, организация и период, страницы. Не регистры, двоичные данные и поля с «пароль», «секрет», «токен» в имени не читаются — [подробности](RELEASE-1.3.md#чтение-регистров) |

**Чтение — Бухгалтерия** (по регистру бухгалтерии «Хозрасчётный»; в Управлении торговлей отвечают отказом с подсказкой, чем заменить):

| Инструмент | Что делает |
|---|---|
| `read.analytics.get_debtors` / `read.analytics.get_creditors` | Дебиторка (сч. 62) / кредиторка (сч. 60) по контрагентам, на дату (`asOf`). `aging=true` — по срокам: просрочено / в срок / срок не задан, просрочка по дням, возраст долга от даты документа, документы расчётов; `overdueOnly=true` — только просроченные |
| `read.analytics.get_unpaid_invoices` | Неоплаченные и частично оплаченные счета покупателям: оплачено по регистру «Оплата счетов», остаток, отгрузка по счёту, сальдо покупателя по 62 для сверки |
| `read.analytics.get_inventory` | Остатки товаров (сч. 41/10/43; в УТ — по регистру «Себестоимость товаров») с суммой, артикулом и группой, на дату в прошлом (`asOf`), с поиском по названию и артикулу (`query`), отбором по группе номенклатуры (`group`: название, путь `Родитель/Группа` или `Ref_Key`) и разбивкой по складам (`groupBy: warehouse`); итоги по группам товаров (`groupBy: itemGroup`) |
| `read.accounting.get_account_turnover` | ОСВ по счёту за период (`51`, `60`, `90.01`…): сальдо на начало/конец и обороты Дт/Кт, итогом и по субсчетам |
| `read.accounting.get_account_card` | Карточка счёта за период: каждое движение — дата, документ, содержание, Дт/Кт, корреспондирующий счёт и аналитика, остаток после движения; сальдо на начало и конец сверено с регистром. Отбор по контрагенту (`counterpartyRef`) или любому субконто (`dimensionRef`). Ответ постраничный (`offset`, `nextOffset`, `snapshot`; не больше 100 строк и 45 000 символов за раз); итоги по месяцам, корреспондирующим счетам, контрагентам и договорам своей или корреспондирующей стороны — `groupBy`, без строк — `summaryOnly` |
| `read.accounting.get_balance_origin` | Откуда сложилось сальдо: из каких документов состоит остаток на дату и с какого времени он висит — по документам расчётов из сальдо 1С или по истории движений на несколько лет назад |
| `read.counterparty.get_reconciliation` | Данные для акта сверки с контрагентом по 60/62/76: сальдо на начало и конец «в пользу организации / контрагента», строки по документам, обороты, итоги по договорам (`contractRef` — один договор) |
| `read.accounting.check_month_close` | Проверка месяца (`month=YYYY-MM`): закрытие выполнено и без ошибок, закрыты ли предыдущие месяцы, непроведённые документы, красное сальдо (деньги и товары в минусе, расчёты 62/60 не на той стороне), остатки на 90/91 и 20–26/44 после закрытия и документы, внесённые после закрытия, амортизация при ОС/НМА, реализации с НДС без счёта-фактуры. По каждой проверке — статус и строки |
| `read.accounting.get_document_postings` | Проводки одного документа (любого `Document_*`) из регистра Хозрасчетный: Дт/Кт с кодами счетов и субконто, суммы, итоги и свод по корреспонденциям. Субконто — `ExtDimensionDr1..3`/`ExtDimensionCr1..3`: на БП 3.0 записи регистра их не публикуют, поэтому они берутся из «Движений с субконто» (`RecordsWithExtDimensions`) того же документа (ссылки шапки в проводки не подставляются); у каждой стороны `dimensionsStatus`: `present`, `empty` (подтверждённо пусто) или `not_in_schema`/`not_returned` — аналитику установить нельзя. Пример: `{"documentEntity": "Document_РегламентнаяОперация", "documentRef": "919a75d1-7f6a-11f1-86c3-74563c4bf0d1"}` |
| `read.accounting.get_settlement_settings` / `read.accounting.get_contract_settlement_settings` (устаревшее имя, удаляется в 2.0) | Точная сохранённая настройка счетов расчётов для договора, контрагента или группы — [подробнее](SETTLEMENTS.md) |

**Чтение — Управление торговлей и оперативный учёт** (регистры УТ 11; те же есть в КА 2 и ERP 2; проверено на УТ 11.5):

| Инструмент | Что делает |
|---|---|
| `read.analytics.get_warehouse_stock` | Остатки на складах по регистру «Товары на складах» (оперативный учёт УТ 11, КА 2, ERP 2; проверено на УТ 11.5; в УТ это единственный источник остатков): количество в наличии (`inStock`) и к отгрузке (`toShip`), без сумм. | `read.analytics.get_sales_report` | Продажи в разрезах на выбор (Бухгалтерия и УТ): до трёх разрезов — товар, группа, склад, подразделение, менеджер, клиент, организация, операция, период (день, неделя, месяц, квартал); выручка, себестоимость и маржа; сравнение с прошлым периодом или годом, сортировка и ABC |
| `read.analytics.get_purchases_report` | Закупки в разрезах (УТ): поставщик, товар, группа, склад, подразделение, менеджер, организация, операция, период; сумма, количество и скидка; сравнение периодов, сортировка и ABC |
| `read.analytics.get_partner_settlements` | Долги клиентов и поставщикам по управленческим расчётам с партнёрами (УТ 11, КА 2, ERP 2; проверено на УТ 11.5): долг, предоплата, просрочка и разбивка по срокам по плановой дате погашения, по каждому партнёру. Не счёт 62/60 — в Бухгалтерии это `get_debtors` / `get_creditors`; по менеджерам (`byManager`, отбор `managers`); платёжный календарь (`schedule`: по дням, неделям, месяцам вперёд) |

**Запись (✍️ требует включения, работает через dry-run → `confirm=true`):**

В Управлении торговлей те же инструменты пишут документы УТ: оплаты — поступление и списание безналичных, ПКО и РКО; счёт — счёт на оплату клиенту; реализация товаров и услуг (`create_act`), приобретение, возвраты, счета-фактуры. Счёт поставщика, платёжное поручение и акт оказания производственных услуг в УТ — отказ с подсказкой замены. Что в какой конфигурации проверено вживую — [SUPPORT.md](SUPPORT.md).

| `write.pricing.create_price_setting` | Установка цен номенклатуры по одному виду цен (Управление торговлей 11; Бухгалтерия 3.0 — по типу цен): документ создаётся непроведённым, цены вступают в силу после `post_document`. Предпросмотр — «было → станет» по каждой позиции и предупреждения: зависимые виды цен (наценка на этот вид) через OData не пересчитаются; у позиции есть цена с более поздней датой; цена на тот же момент — отказ. После проведения движения регистра цен сверяются со строками документа до копейки. Проверено на копии рабочей УТ 11.5 и на живой БП 3.0: создание, проведение, сверка, отмена, пометка удаления |
| `write.document.post_document` | Провести / отменить проведение (1С формирует проводки); с `expectedDataVersion` — с проверкой версии документа и журналом операции; явное повторное проведение — `post=true`, `repost=true` и точная версия |
| `write.accounting.set_settlement_settings` / `write.accounting.set_contract_settlement_settings` (устаревшее имя, удаляется в 2.0) | Настройка счетов расчётов и авансов для договора, контрагента или группы (регистр «Счета учёта расчётов с контрагентами») — [подробнее](SETTLEMENTS.md) |
| `write.document.align_bank_payment_amounts` | Суммы строк расшифровки платежа (несколько строк — по `lineAmounts` или уже сходящимся суммам) существующего непроведённого рублёвого банковского документа — по сумме документа (платёж, взаиморасчёты, НДС по ставке строки) — [подробнее](SETTLEMENTS.md#суммы-расшифровки-платежа) |
| `write.document.apply_bank_settlement_settings` | Договор и счета расчётов/авансов по сохранённым настройкам — в существующий непроведённый банковский документ — [подробнее](SETTLEMENTS.md#перенос-счетов-в-банковский-документ) |
| `write.counterparty.create_group` / `write.counterparty.set_group` | Группа контрагентов / перенос контрагента в группу (с проверкой цепочки и версии) |
| `write.operation.status` | Статус операции записи по `operationId`; после таймаута сверяет с 1С (созданный объект — по назначенному `Ref_Key`, правку строк — по числу строк). Найденный результат фиксирует как успех; отсутствие результата закрывает операцию только с `markNotApplied=true` после ручной сверки |
| `write.entity.mark_for_deletion` | Пометить на удаление / снять пометку (мягкое удаление) |

Параметры каждого инструмента — в [справочнике параметров](TOOLS-REFERENCE.md), он собирается из кода.

Инструменты записи и бухгалтерские проверены на живых базах **1С:Бухгалтерия предприятия 3.0**, инструменты чтения — ещё и на **Управлении торговлей 11.5**. В Управлении торговлей запись — только установка цен, справочники и складские документы, проверенные на копии рабочей УТ 11.5, — см. [Безопасность](WRITE.md).
