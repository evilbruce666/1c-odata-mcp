# Запись и безопасность

**По умолчанию сервер работает только на чтение.** Запись включается осознанно, через **два независимых предохранителя**:

1. **Глобальный рубильник** `READ_ONLY=false`.
2. **Флаг базы** — `ODATA_WRITABLE=true`, если база одна (`ODATA_BASE_URL`), или `ODATA_DB_<ИМЯ>_WRITABLE=true` для каждой из нескольких баз. Базы без него остаются read-only даже при снятом глобальном. Если настроено несколько баз, запись требует явного `database`, в том числе предпросмотр. Так можно открыть запись в одну базу (напр. ИП) и защитить другие (напр. ООО).

Дополнительно при записи:

- **только в бухгалтерской базе** — если в составе OData нет регистра бухгалтерии «Хозрасчётный» (Управление торговлей, другая небухгалтерская конфигурация или Бухгалтерия, где его забыли опубликовать), инструменты записи отвечают отказом; если проверить состав базы не удалось, запись тоже не выполняется. Исключения в Управлении торговлей (что из них и когда проверено на копии рабочей УТ 11.5 — [SUPPORT.md](SUPPORT.md)): установка цен; справочники — партнёры, контрагенты, их банковские счета и контактные лица, договоры и соглашения, номенклатура и её папки; склад — перемещение, оприходование излишков, списание недостач, пересчёт; деньги — поступление и списание безналичных, приходный и расходный кассовые ордера, заявка на расходование; продажи и закупки — заказ клиента, счёт на оплату, реализация товаров и услуг (`create_shipment`, `create_act`), приобретение, возвраты поставщику и от клиента, заказ поставщику, счета-фактуры выданный и полученный. Для этих документов работают правка строк, копия, поля шапки по белому списку (`update_entity`), `post_document` со сверкой движений регистров (склад, деньги, расчёты с партнёрами, серии) и `mark_for_deletion`. Правку, перемещение и пометку существующей номенклатуры УТ 11.5 через OData отвергает — инструмент отвечает понятным отказом. Розница, кассы ККМ, выплата зарплаты и документы Бухгалтерии без аналога в УТ (акт оказания производственных услуг, счёт поставщика, платёжное поручение) — отказ с подсказкой замены. Регистр с другим именем задаётся в [настройке учёта](ACCOUNTING.md);
- **dry-run по умолчанию** — предпросмотр создания (и добавления/удаления строки документа) возвращает `operationId`; для записи передайте этот же id и те же аргументы вместе с `confirm=true`. При сетевой ошибке повторяйте подтверждение с тем же id, не запускайте новый предпросмотр;
- **защита от неопределённого результата POST** — локальный журнал сохраняет отпечаток запроса и результат. Повтор с тем же id и теми же аргументами вернёт сохранённый итог без второго POST; если соединение оборвалось и исход неизвестен, сервер заблокирует повтор и попросит сверить результат в 1С. Сверку делает `write.operation.status`: создаваемому объекту MCP сам назначает `Ref_Key` (UUIDv1, назначается при предпросмотре), поэтому повтор с той же ссылкой 1С отвергает на уровне уникального индекса, а после таймаута объект находится простым GET — и для документов, и для справочников. Правка строк документа сверяется по числу строк. Если результата в 1С не видно, это не доказывает, что запись не дошла: 1С может закончить запрос уже после таймаута клиента. Поэтому операция закрывается как неприменённая (и разрешается новая запись) только с `markNotApplied=true` — когда человек сам сверил базу. По желанию в «Комментарий» документов можно дописывать видимую метку `[op:<operationId>]` (`ODATA_WRITE_OPERATION_MARKER=true`);
- **проверка сохранения** — после изменения объекта поля перечитываются: успех только если 1С сохранила всё, что отправлено; иначе — ошибка с именами несохранённых полей (1С может перезаполнить часть полей сама при записи), без автоматического повтора;
- **читаемый предпросмотр** — рядом с `payload` предпросмотр отдаёт `view`: подписи полей по-русски, названия вместо GUID (контрагент, договор, номенклатура, счета учёта, организация), строки табличных частей, у изменения — «было → станет». Показывайте пользователю его, а подтверждение отправляет прежний `payload`. Названия — до 4 запросов к справочникам; интеграциям с массовой записью без человека в цикле вид можно выключить: `ODATA_PREVIEW_VIEW=false`;
- **договор по умолчанию** — если `contractRef` не указан, а у контрагента ровно один подходящий договор (вид «с покупателем»/«с поставщиком», та же организация), он подставляется, как в форме 1С; иначе предпросмотр предупреждает: без договора 1С документ не проведёт;
- **мягкое удаление** — `write.entity.mark_for_deletion` ставит пометку (как в 1С); жёсткого `DELETE` нет;
- на стороне 1С в «Состав OData» включаются только нужные объекты, а у пользователя 1С должны быть права на запись.

**Приватность данных.** Обычно сервер — локальный процесс на вашей машине: он ходит только в вашу базу 1С (по Basic-аутентификации) и отдаёт данные вашему MCP-клиенту. Если вы сами подняли его [по HTTP](CONNECTING.md#подключение-по-http-опционально), данные идут и по этому соединению; TLS настраивается отдельно. Никаких сторонних серверов проекта в цепочке нет. Если использовать **локальную модель** (Ollama, LM Studio), данные 1С вообще не покидают вашу сеть. Секреты — только из `.env` (или блока `env` конфига); пароль и заголовок авторизации в логи не попадают. Параметры запроса с названиями и ИНН в логе видны только при `LOG_LEVEL=debug`; сообщения 1С об ошибках пишутся и на обычном уровне.

Журнал защиты от повторной записи хранится локально в `~/.1c-odata-mcp/write-journal` (путь можно изменить через `ODATA_WRITE_JOURNAL_DIR`). В нём нет полного payload: сохраняются hash запроса, статус операции и ограниченная сводка результата (`Ref_Key`, `Code`, `Number`). Успешные, отклонённые и неподтверждённые предпросмотры удаляются через 90 дней; операции с неизвестным результатом хранятся год (раньше удалять нельзя: это разрешило бы опасный повтор). Раз в час чистятся и служебные файлы: зависшие `.tmp` и «осиротевшие» `.lock`. В Docker смонтируйте каталог журнала на том (`ODATA_WRITE_JOURNAL_DIR`), иначе защита теряется вместе с контейнером.

## Как включить запись

1. `READ_ONLY=false` и флаг базы (`ODATA_WRITABLE=true` или `ODATA_DB_<ИМЯ>_WRITABLE=true`) — в блок `env`
   конфига MCP-клиента или в `.env`.
2. Уберите `TOOLS_PROFILE=read`, если он есть в конфиге (он стоит в примерах): иначе инструменты записи не
   подключаются.
3. Опубликуйте объекты и дайте пользователю 1С права — таблицы ниже.
4. Полностью перезапустите MCP-клиент.

Подробнее про переменные — [CONNECTING.md → Включение записи](CONNECTING.md#включение-записи-опционально).
Запись по HTTP (бот, своё приложение) — отдельные условия: [CONNECTING.md → Запись по HTTP](CONNECTING.md#запись-по-http).

Сверх состава для чтения ([CONNECTING.md](CONNECTING.md#уровень-1-публикация-odata-в-1с)). Пользователю 1С нужны

**Для записи документов с контрагентом (реализация, поступление, оплаты) рекомендуется:**

| Категория | Объекты | Зачем |
|---|---|---|
| Регистры сведений | СчетаУчетаРасчетовСКонтрагентами | счета расчётов и авансов по настройке договора/контрагента (76.09 вместо 62.01, валютные 62.21 и т.п.). 1С через OData эту настройку сама не применяет — без регистра MCP ставит стандартные 62.01/62.02, 60.01/60.02 и пишет об этом в предпросмотре |
| Регистры сведений | СчетаУчетаНоменклатуры | счета учёта, доходов и расходов по номенклатуре |

**Права для настроек счетов расчётов и групп контрагентов** ([SETTLEMENTS.md](SETTLEMENTS.md)) — у каждого инструмента свои объекты и запросы:

| Инструмент | Что читает | Что меняет |
|---|---|---|
| `read.accounting.get_settlement_settings` | регистр «Счета учёта расчётов с контрагентами» (GET записи), контрагенты, договоры, организации, валюты | — |
| `write.accounting.set_settlement_settings` | то же | **регистр**: POST (создание записи) или PATCH (изменение) |
| `write.document.apply_bank_settlement_settings` | регистр (GET списка для подбора), контрагенты и группы, договоры, валюты, план счетов | **банковский документ** (PATCH); регистр не меняет |
| `write.counterparty.create_group` | контрагенты (родительская группа) | **справочник контрагентов**: POST |
| `write.counterparty.set_group` | контрагенты | **справочник контрагентов**: PATCH (`Parent_Key`) |

Право **записи регистра** нужно только для `set_settlement_settings`; для остальных достаточно чтения регистра и права изменения документа или справочника. Без нужного права 1С отвечает 500 «Нарушение прав доступа!» — коннектор показывает это как отказ «Нет прав в 1С» и ничего не меняет. Наличие объекта в `$metadata` право записи не подтверждает: чтение, добавление и изменение проверяются отдельно. На облачных площадках (Scloud и др.) права пользователя OData может настраивать только провайдер — тогда нужен запрос в его поддержку.

## Документы и проведение

- **Документы создаются непроведёнными.** Проводки формирует сама 1С при проведении (`write.document.post_document` или вручную) — сервер не «рисует» проводки напрямую.
- **Повторное проведение — явное действие.** Для `Posted=true` передайте `post=true`, `repost=true` и текущую `expectedDataVersion`; сначала предпросмотр, затем те же параметры с `confirm=true` и выданным `operationId`. Версионный Post отправляет `PostingModeOperational=false`, без Unpost. Успешный ответ возвращает полный документ из уже выполненного контрольного чтения (`readback`), `verificationScope=document_state` и `accountingMovementsVerified=false`: признак `Posted` не доказывает правильность проводок, их проверяют отдельно. Завершённый `operationId` возвращает квитанцию без нового Post/GET (`verificationScope=journal_receipt`, `readbackFetched=false`); полный документ в журнале не сохраняется. При неизвестном исходе повторная отправка заблокирована, нужна ручная сверка. Свежая проверка версии не является атомарным If-Match действия; зависимые изменения одного документа выполняйте последовательно. Ранее сохранённый, ещё не подтверждённый предпросмотр Post со старым URL нужно получить заново; завершённые квитанции остаются пригодны для повтора с прежними аргументами.
- **Регламентные операции не создаются.** Закрытие месяца, амортизацию, расчёт себестоимости/НДС генерирует обработка «Закрытие месяца» своими алгоритмами — через OData их не запустить. Читать (`read.document.search_documents`/`read.document.get_document`) и проверять результат (`read.accounting.check_month_close`) можно.

## Деньги: несколько строк, перевод, эквайринг

- **Оплата несколькими строками** — `settlementLines` в `create_bank_writeoff` и `create_payment`, сумма строк равна `amount`;
  как разнести сумму, решает пользователь. Бухгалтерия — по договорам одного контрагента `{contractRef, amount}`,
  счета расчётов подбираются по договору каждой строки. Управление торговлей — по документам `{basisRef, amount}`
  (оплата поставщику — по приобретениям и заказам поставщику, поступление от клиента — по реализациям и заказам
  клиента). Выровнять суммы строк существующего документа Бухгалтерии — `align_bank_payment_amounts` с `lineAmounts`.
- **Перевод между своими счетами** (Бухгалтерия) — `create_bank_writeoff` с видом «ПереводНаДругойСчет» и
  `targetBankAccount`: счёт той же организации, в той же валюте. Схему (напрямую по 51 или через 57.01) выбирает 1С —
  заметка подскажет, нужен ли документ поступления.
- **Эквайринг** (Бухгалтерия) — `create_payment` с видом «ПоступленияОтПродажПоПлатежнымКартамИБанковскимКредитам»:
  банк-эквайрер и договор с ним, `amount` — поступило на счёт, `commission` — комиссия банка со счётом
  (`corrAccount`, напр. «91.02») и статьёй. Проводки Дт 51 Кт 57.03 и Дт 91.02 Кт 57.03.
- **Не создаются**, отказ с причиной: перечисление зарплаты (по ведомости в 1С) и снятие наличных (1С проводит его без
  проводок). Что проверено вживую по каждому виду — [SUPPORT.md](SUPPORT.md).
