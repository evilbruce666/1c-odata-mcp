# Интеграциям и ботам

- Сервер можно поставить рядом с ботом или своим приложением: [HTTP](CONNECTING.md#подключение-по-http-опционально) — чтение, запись отдельным экземпляром ([условия](CONNECTING.md#запись-по-http)), с токеном и проверкой адреса
- `TOOLS_PROFILE=read` или точный список инструментов — меньше описаний в контексте модели
- Ответы со схемой (`structuredContent`), вид ошибки отдельным полем, длинные списки — страницами
- Склады и организации отдаются со своими `Ref_Key`: отбор для отчёта собирается один раз и передаётся дальше
- **Ответственный от имени пользователя бота.** `read.catalog.list_users` — пользователи 1С для привязки (поиск по имени, по умолчанию только действующие); `refs` — проверить сохранённые привязки пачкой. Ссылку передавайте в `responsibleRef` любого инструмента создания документа: коннектор проверит пользователя до записи и поставит его в «Ответственный» или «Менеджер». Все записи идут под одним пользователем OData — «Ответственный» показывает, кто из людей дал команду, а журнал «кто что сделал» ведите на стороне бота.

## Несколько баз и несколько организаций

Это разные случаи:

- **Несколько отдельных баз** (разные OData-адреса) — один сервер обслуживает все; имя базы передаётся параметром `database`. Чтение без него идёт в базу по умолчанию и помечает это в ответе (`databaseDefaulted`), запись без него отказывает. Настройка в `.env` — см. [docs/CONNECTING.md](CONNECTING.md#несколько-баз-1с). Пример запроса: «сравни выручку buh и torg за май».
- **Несколько организаций (юрлиц) в одной базе** — отдельное подключение не нужно, работает фильтр `organization`. Пример: «остатки по организации Ромашка».

## Большие ответы

- **Большие ответы приходят частями.** Один ответ — не больше примерно 45 000 символов: иначе клиент уносит его в файл и теряет конец. Для клиента с малым контекстом предел можно уменьшить (`ODATA_MAX_RESPONSE_CHARS`, от 10 000). Текст ответа — компактный JSON. Итоги, предупреждения и `truncated` идут в ответе раньше списков. Вложенные списки продолжения не имеют: то, что не поместилось, перечислено в `truncatedLists`. Если ответ сократить нечем, например из-за одной длинной строки, в нём `overLimit: true`. Читайте дальше с `offset` из `nextOffset`, пока он есть; `truncated: true` без `nextOffset` значит, что продолжения нет и нужно уточнить запрос. Итоги всегда по всем строкам. Заполненный `limit` тоже даёт `nextOffset`: последняя страница может оказаться пустой. `snapshot` из прошлой страницы показывает, изменились ли данные между страницами (`dataChanged`, начните заново); у `search_documents` этой метки нет: новый документ может дать повтор строки, а удалённый — пропуск. Защитный максимум строк — `ODATA_MAX_ROWS`. Большая выборка, не успевшая за `ODATA_TIMEOUT_MS`, читается по месяцам или группам счетов. Один вызов всё равно ограничен таймаутом клиента (обычно 60 секунд), поэтому на очень большой базе сужайте период. Если клиент отменил вызов, запросы к 1С чтения останавливаются и не занимают очередь. Общий лимит на вызов задаёт `ODATA_TOOL_DEADLINE_MS` (по умолчанию без лимита); запись отмена и лимит не прерывают. Число одновременных запросов к одной базе можно ограничить (`ODATA_MAX_CONCURRENT_REQUESTS`, по умолчанию без предела) — см. `.env.example`.

## Ответы и имена инструментов

- **Типизированные ответы.** У всех 93 инструментов объявлен `outputSchema` — клиенты, поддерживающие `structuredContent` (не только текстовый JSON), могут типизировать ответ, не парсить текст.
- **Имена инструментов.** Трёхсегментный `dot-notation`: `<read|write>.<категория>.<имя>` (напр. `read.analytics.get_debtors`, `write.sales.create_shipment`) — группирует инструменты по категории и сразу видно, чтение это или запись.
